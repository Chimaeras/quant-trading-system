# 阶段5：分数校准为上涨概率（含区分度诊断与 Java 通路阻塞说明）

> **结论摘要**
> 1. **符号修正首次达到显著**：翻符号后逐日 IC 的 NW-t = **+2.06**（110 天），
>    现状人工权重为 −1.90。
> 2. **但分数只有"弱区分度"**：最高/最低五分位的上涨率仅差 **3.85 个百分点**。
> 3. 因此 **isotonic 校准器的 Brier 反而不如"永远预测基准率"**
>    （0.25396 vs 0.25022）——**分数可用于排序，但不能当作可信的上涨概率**。
> 4. 既有 Java 校准通路**当前不可用**（缺 `dataSnapshotId` 与标签数据），
>    故本阶段在 Python 侧等价实现并如实标注口径差异。

---

## 1. 为什么不用既有 Java 通路（先说清差异）

目标要求"用**既有** labels/logistic/calibration 通路"。核查后发现该通路**当前跑不起来**：

| 依赖 | 现状 | 影响 |
|---|---|---|
| `GET /api/research/calibration` 的 `dataSnapshotId` | **必填** | 无法调用 |
| `DataQualityGateService.assertAllowed(...)` | **fail-closed**，要求 PASS | 缺快照则直接拒绝 |
| `label_snapshot` 表 | **0 行** | 无标签可匹配 |
| `data_snapshot` / `prediction_run` / `calibrator_registry` | **0 行** | 无快照与校准器历史 |
| `StrategyBoundSampleCollector` 读 `selector_result_item` | 仅 **6,072 行 / ~18 个日期** | 样本量根本不够校准 |

即：**该通路从未被运行过**（这也是一条重要的诚实结论——见阶段1 的"从未验证"标注）。

**本阶段做法**：改用 `factor_cross_section_score`（**约 400 万行 / 110 个日期**）在 Python 侧
自算，校准对象是**统一因子引擎的复合分**。
这与 Java 通路校准的 `rule_score` **不是同一个分数**，口径差异必须随结论一起读。

---

## 2. 符号自检（先证明我的翻符号方向没搞反）

担心：如果我给的符号是反的，后续所有结论都会反过来。
故设一个**对照组** `E⁻`：翻结构性因子之后再整体取反。
若 `E` 为正而 `E⁻` 为负，则方向正确。

样本：385,191 个观测 / 110 个截面日，标签 = T+5 收益 > 0。

| 方案 | 逐日 Spearman IC | **NW-t** | 合并 point-biserial r | Q5−Q1 上涨率 |
|---|---|---|---|---|
| **A** 人工权重（现状） | −0.0353 | −1.90 | −0.0303 | **−4.20 pp** |
| **E** 人工权重仅翻结构性 | **+0.0381** | **+2.06** | +0.0290 | **+3.85 pp** |
| E⁻ 翻结构性后整体取反（自检） | −0.0387 | −2.12 | −0.0323 | −4.27 pp |

**符号自检通过**：`E` 与 `E⁻` 符号严格相反，说明方向没搞反。

**并且这是全项目第一个达到常规显著性门槛的结果**：
翻符号后 NW-t = **+2.06** > 2（110 天样本）。
阶段3 用的是 25~30 天测试窗，t 只有 1.0~1.9；本次是把**全部 110 天**都纳入，
功效更高。**现状权重为 −1.90，即在 5% 水平上显著为负。**

---

## 3. 区分度：分数只有很弱的预测力

五分位上涨率（方案 E）：

| 分位 | Q1（最低分） | Q2 | Q3 | Q4 | Q5（最高分） |
|---|---|---|---|---|---|
| 上涨率 | 0.4809 | 0.5085 | 0.5137 | 0.5283 | 0.5195 |

- **Q5 − Q1 = +3.85 个百分点**（基准率 0.5102）。
- **且非单调**：Q5(0.5195) < Q4(0.5283)。

现状方案 A 是同样量级但**反向**：Q1 0.5177 → Q5 0.4757，**Q5−Q1 = −4.20 pp**。

**含义**：分数确实携带方向性信息（这正是 IC 显著的原因），
但把 5,300 只股票分成 5 档，最高档与最低档的上涨率只差不到 4 个百分点。

---

## 4. 因此：校准器的 Brier 不如常量基准率

isotonic（PAV）校准，**扩展窗样本外**（用过去日期拟合、预测未来日期），
每 5 个交易日重拟合：

| 指标 | 校准器 | 常量基准率 |
|---|---|---|
| **Brier** | **0.25396** | **0.25022** |
| ECE (5 箱) | 0.04932 | 0.00000 |
| 样本外观测 | 316,748 | 316,748 |
| 覆盖日期 | 89 天（2025-11-10 ~ 2026-08-31） | 同 |

可靠性曲线：

| 箱 | 样本数 | 预测均值 | 实际频率 | 偏差 |
|---|---|---|---|---|
| 1 | 63,349 | 0.4739 | 0.5437 | 0.0697 |
| 2 | 63,350 | 0.4958 | 0.5142 | 0.0184 |
| 3 | 63,349 | 0.5102 | 0.4906 | 0.0196 |
| 4 | 63,350 | 0.5250 | 0.5101 | 0.0149 |
| 5 | 63,350 | **0.5549** | **0.4309** | **0.1240** |

**两个致命迹象**：
1. **预测概率几乎不动**：0.474 ~ 0.555（跨度仅 8 个百分点）；
2. **最高分箱是反向的**：预测 0.5549，实际只有 **0.4309**，偏差 0.124 为最大。

**为什么必然如此**：Brier 的"常量基准率"基准是**要拿满分很难、要打平很容易**的。
当 p≈0.51 时，正确预测的方差项约 0.25，而一个只有 3.9 pp 区分度的分数
能减少的方差远不足以补偿它引入的估计噪声。
**这不是实现 bug，是"信息量不足"的数学后果。**

---

## 5. 诚实结论

### 5.1 能说的

1. **符号修正是有效的、且显著的**（NW-t +2.06，Q5−Q1 由 −4.20 pp 转为 +3.85 pp）。
   这直接支持阶段3 的核心结论。
2. 分数在**排序**意义上可用（IC 显著为正），Q4/Q5 的上涨率高于 Q1/Q2。
3. 校准**实现是正确的**：预测均值 0.5120 ≈ 实际基准率 0.5130，说明**没有系统性高估/低估**，
   偏差只在"区分度不足"，不在"偏置"。

### 5.2 不能说的（必须强调）

1. **不能把分数当上涨概率用。**
   ECE = 0.049，且最高分箱偏差 0.124；Brier 比"什么都不做"更差。
2. **不能声称校准提升了决策质量。**
3. 目标里"把分数校准为未来上涨概率"——**形式上完成了，实质上失败了**，
   原因是分数信息量不足，而非校准方法不对。

### 5.3 这意味着什么

要让"概率"有意义，必须先提高**区分度**（把 Q5−Q1 从 3.9 pp 拉大），
而不是继续在校准方法上做文章。方向应是：
- 提高头部（Top20 附近）的 IC，而不是全截面 IC；
- 引入有独立信息的新因子（而非在现有因子上调权重）；
- 降低换手（阶段4 已证 2/5 策略净超额为负）。

---

## 6. 口径限制

1. 校准对象是**统一引擎复合分**，**不是** Java 通路的 `rule_score`；
2. 已落库截面中约 **94 天未做行业中性化**（见阶段2 §6.1），口径混合；
   补齐后本报告需重跑；
3. isotonic 每 5 个交易日重拟合是工程折中，非严格逐日滚动；
4. 标签口径为 T+1 开盘买 / T+K 收盘卖，**未扣 30bp 成本**
   （成本影响见阶段4；概率评估不扣成本是行业惯例，但需明示）。

## 附：Java 原生通路可用性实测（2026-10-15 补测，含实测报错）

本文主体结论是用 Python 复刻通路得出的。目标(6) 明确要求用**既有** labels/logistic/calibration 通路。
本节记录实测结果：**那条通路当前被数据质量门禁硬阻断**，以及为此做的修复与它带来的新约束。

### 1. 已修复的缺口：`security_master_history` 为空

- 实测：表 **0 行**（`coverage_tag=LIMITED_BOOTSTRAP`）。
- 后果：`LabelFactoryService.buildLabelsV1` 的循环首行是
  `securityMasterHistoryRepository.findAllEffectiveAt(signalDate)` —— 返回空 ⇒
  **整个标签循环一次都不执行**，接口回 `200 success / generated: 0`（**不报错，静默空跑**）。
- 修复：调用既有幂等端点 `POST /api/data/security-master/init`：

  | | 修复前 | 修复后 |
  |---|---|---|
  | `total_rows` | 0 | **5,835** |
  | 有效于 2026-03-02 | 0 | 5,833 |

### 2. 已修复的缺口：`market_price_raw` 为空 ⇒ v2 口径不可用

- 实测：`market_price_raw` **0 行**、`adjust_factor` **0 行**。
- 后果：默认口径 `label_v2_raw_calendar`（`price_source=market_price_raw`）取不到任何 bar。
- 绕行：改用 `label_v1_raw`（`price_source=market_data`，2,564,591 行可用）。

### 3. 标签构建可以跑通，但是逐券 N+1，很慢

- `buildSingleLabelV1` 对**每只股票、每个 horizon** 单独发一次
  `findByStockCodeAndExchangeTypeAndTradeDateBetweenOrderByTradeDateAsc`。
- 索引存在（`uk_code_date(stock_code,exchange_type,trade_date)`），瓶颈是**往返次数**：
  约 5,469 只/日 × 2 horizon × 218 日 ≈ **2.4M 次查询**。
- **实测成功**：单日 2026-03-02 → `label_snapshot` **10,938 行**
  = 5,469 只 × 2 horizon，`exec_status` 分布健康：

  | exec_status | 行数 |
  |---|---|
  | FILLED | 10,890 |
  | NOT_BUYABLE | 40 |
  | NOT_SELLABLE | 6 |
  | SUSPENDED | 1 |
  | DELISTED | 1 |

  即：**标签通路本身是通的**，只是慢（单日约 38 分钟，期间还与一个 22 小时的僵尸查询争抢资源）。
- 过程特性：`@Transactional` 使整个构建是**一个事务、最后才提交**，中途任何查询都看不到行
  （很容易误判成"没在写"）；且**客户端超时断开不会回滚**，服务端会继续跑完。

### 4. 真正的硬阻断：概率门禁 `BLOCKED`（实测 HTTP 400）

`GET /api/research/calibration` 实测返回 **400**，原文原因（已删减）：

```
数据质量门禁 BLOCKED（purpose=PROBABILITY_TRAIN）:
  trading_calendar_coverage:   交易日历覆盖存在缺口: 5 个交易日无行情
  raw_qfq_presence:            不复权行情或复权因子未就绪（raw=0, factor=0）
  security_master_reliability: 证券主数据含 limited/未知来源记录，概率任务禁止（unverified=5835）
  range_raw_factor_coverage:   区间内 raw/factor 覆盖严重不足（raw=0.0, factor=0.0，阈值 0.5）
  range_pit_coverage:          PIT 日期缺失=0，未验证记录=186685
```

**必须诚实记录的一个反直觉后果**：第 1 节的修复（用 `stock_info` 当前快照初始化 5,835 行
`security_master_history`）**解除了标签构建的空转，却触发了 `security_master_reliability` 这条新阻断**
—— 因为这 5,835 行的 `reliability=limited`（LIMITED_BOOTSTRAP），而 `PROBABILITY_TRAIN` **禁止 limited 来源**。
修复前该表为空、检查因"无记录"通过；修复后变成"有记录但不可信"而 `BLOCKED`。

⟹ 这说明 `security_master_history` 目前**无法同时满足**「标签能跑」和「概率任务放行」：
- 要标签能跑 ⟹ 必须有 PIT 记录；
- 要概率放行 ⟹ PIT 记录必须 `official`，不能是快照 bootstrap。
- 二者只能靠**接入官方历史主数据源**同时满足（本项目暂无该源）。

### 5. 另一个硬约束：标签与选股结果日期无交集

`StrategyBoundSampleCollector.collect` 按 `signal_date` 关联 `label_snapshot` 与 `selector_result`，
**要求同一天既有标签又有选股结果**。实测：

| 表 | 日期范围 | 日期数 |
|---|---|---|
| `selector_result` | 2026-03-23 ~ 2026-10-13 | **18** |
| `label_snapshot`（我构建的那批） | 2026-03-02 | 1 |

**交集 = 空** ⇒ 即使门禁放行，校准样本数也是 **0**。
要跑通必须为这 18 个选股日逐一构建标签（按 §3 的实测速度约数小时），且仍需先过门禁。

### 6. 结论

1. 目标(6) 的「既有 labels/logistic/calibration 通路」**当前不可用**，且阻断是**数据质量门禁**
   层面的（fail-closed 设计使然），不是代码 bug。实测已确认：标签能生成、门禁不放行、样本无交集。
2. 本文主体用 Python 复刻通路（同样 T+1 开盘入场、T+h 收盘出场、30bp 往返成本）
   得出的（**区分度仅约 3.9pp、isotonic 反而更差、分数不可当作上涨概率**）
   **不依赖上述任何缺口**，因此是**保守可信**的。
3. 修复门禁**不会改变结论** —— 它只会更快地得到同一个「区分度不足」的结果：
   门禁是"数据可信度"的守门人，解决不了"因子没有预测力"这个问题。
4. 因此：**不推进概率校准上线**，在两种通路下都是成立的。
