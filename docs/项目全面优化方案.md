# 量化交易系统 — 全面优化方案

> 审查范围：backend-java / compute-python / web / database / docker / 架构
> 审查日期：2026-05-19

---

## 一、安全性问题 (P0 — 必须立即修复)

### 1.1 默认管理员密码硬编码

**位置**: `DataInitializer.java:28`

```java
admin.setPassword(passwordEncoder.encode("123456"));
```

每次启动都会检查 admin 用户是否存在，密码固定为 `123456`。任何知道该项目的人都能登录。

**修复**: 改为从环境变量读取初始密码，首次登录强制修改。

### 1.2 Spring Security 所有 API 已开放 — 认证形同虚设

**位置**: `SecurityConfig.java:38-51`

```java
.requestMatchers("/api/auth/**").permitAll()       // 正确
.requestMatchers("/api/backtest/**").permitAll()    // 不应该
.requestMatchers("/api/selector/**").permitAll()    // 不应该
.requestMatchers("/api/analysis/**").permitAll()    // 不应该
.requestMatchers("/api/data/**").permitAll()        // 不应该
.requestMatchers("/api/market/**").permitAll()      // 不应该
.requestMatchers("/api/scoring/**").permitAll()     // 不应该
.requestMatchers("/api/llm/**").permitAll()         // 不应该
.requestMatchers("/api/chat/**").permitAll()        // 不应该
.requestMatchers("/api/**").authenticated()         // 这条永远不生效
```

所有 API 路径在上层已被 `permitAll()`，导致最后的 `.requestMatchers("/api/**").authenticated()` 永远匹配不到。JWT 认证完全无效。前端虽然有 `localStorage` token 检查，但后端不校验。

**修复**: 只保留 `/api/auth/**` 和 `/actuator/health` 为 `permitAll()`，其余 `/api/**` 统一 `authenticated()`。

### 1.3 CORS 允许所有来源

**位置**: `SecurityConfig.java:61`

```java
configuration.setAllowedOrigins(List.of("*"));
```

配合 `.setAllowedHeaders(List.of("*"))`，这是一个开放的跨域配置。在生产环境中应限制为具体的前端域名。

### 1.4 JWT Secret 写死在 application.yml

**位置**: `application.yml:40`

```yaml
jwt:
  secret: quant-trading-system-secret-key-2026-change-in-production
```

文件名已经提示了"change-in-production"，但代码中没有从环境变量读取的机制。

### 1.5 Token 存储在 localStorage (XSS 风险)

**位置**: 前端 5 处读写 `localStorage.getItem('token')`

localStorage 可被 XSS 攻击读取。应改用 httpOnly cookie 或在 CSP 严格的环境中配合短过期时间。

## 二、前端代码质量问题 (P1)

### 2.1 重复的入口文件

存在 `src/main.ts` 和 `src/main.js` 两个入口文件：

- `index.html` 引用 `main.ts`，但 `main.js` 仍然存在且包含不同的初始化代码（`main.js` 会全局注册所有 Element Plus 图标，而 `main.ts` 不会）
- 两套代码逻辑不同但并存，打包结果不确定

**修复**: 删除 `main.js`，统一使用 `main.ts`。

### 2.2 重复的状态管理文件

存在 `stores/user.ts` 和 `store/user.js` 两个用户状态管理文件：

| 文件 | 路径 |
|------|------|
| TypeScript 版本 | `src/stores/user.ts` |
| JavaScript 版本 | `src/store/user.js` |

两个文件都管理 token，但逻辑不同：
- `stores/user.ts`: `setToken(token)` → 直接存 localStorage
- `store/user.js`: `login(credentials)` → 调 API 后存 localStorage

前端可能同时使用两个 store，导致 token 状态不一致。

**修复**: 删除 `store/user.js`，统一使用 `stores/user.ts`。

### 2.3 TypeScript/JavaScript 混用

项目中 `.ts` 和 `.js` 文件混用：

| 类型 | 文件数 |
|------|--------|
| TypeScript | 17 个源文件 |
| JavaScript | 7 个源文件 |

同一功能存在两套实现（如 `stores/user.ts` vs `store/user.js`）。API 层尤为混乱：`auth.js`, `backtest.js`, `position.js`, `account.js` 是 JS，而 `scoring.ts`, `market.ts`, `chat.ts` 是 TS。

**修复**: 统一为 TypeScript。

### 2.4 前端路由无权限控制

`router/index.ts:43-51` 只检查 token 是否存在，不验证 token 是否有效、是否过期。任何 non-empty 字符串都能通过路由守卫。

## 三、后端代码质量问题 (P1)

### 3.1 AccountService 伪造账户数据

`AccountService.java:38-44`：

```java
private Account createDefaultAccount(Long userId) {
    account.setTotalAsset(BigDecimal.valueOf(500000));     // 固定 50万
    account.setCash(BigDecimal.valueOf(150000));            // 固定 15万
    account.setPositionValue(BigDecimal.valueOf(350000));   // 固定 35万
    account.setTodayPnl(BigDecimal.valueOf(12500));         // 固定盈利
}
```

默认账户数据是硬编码的假数据。金额、持仓市值、当日盈亏都不可信。

**修复**: 默认账户初始资金从配置读取，持仓和盈亏从实际 Position 表统计。

### 3.2 BacktestService 使用随机数模拟回测

`BacktestService.java` import 了 `java.util.concurrent.ThreadLocalRandom`，暗示回测可能使用了随机数而非真实 K 线模拟。

### 3.3 LoginResponse 过期时间硬编码

`AuthService.java:31`：

```java
return new LoginResponse(token, 86400L);  // 硬编码 24小时
```

无论 `application.yml` 中 `jwt.expiration` 配置多少，前端显示的过期时间始终是 86400 秒。

### 3.4 positionCount 返回假数据

`AccountService.java:33`：

```java
result.put("positionCount", 0);  // 可从position表统计
```

注释写了"可从 position 表统计"但返回的是硬编码的 0。

### 3.5 根目录 src/ 残留空壳代码

`E:\Project\quant-trading-system\src\` 目录下有 `org.example` 包的空壳文件（Maven archetype 生成时的残留），与 `modules/backend-java` 完全无关，应删除。

### 3.6 输入验证缺失

大多数 Controller 参数没有 `@Valid` / `@NotBlank` / `@Positive` 等验证注解。如 `MarketController.getStockDetail` 的 `code` 参数允许空字符串。

## 五、部署与基础设施问题 (P2)

### 5.1 InfluxDB 未使用但占用资源

`docker-compose.yml` 定义了 InfluxDB 容器，但后端和 Python 引擎都没有任何 InfluxDB 的配置或连接代码。容器会启动但永远不被使用。

### 5.2 Docker Compose 中明文密码

```yaml
MYSQL_ROOT_PASSWORD: 123456
DOCKER_INFLUXDB_INIT_PASSWORD: 123456
DOCKER_INFLUXDB_INIT_ADMIN_TOKEN: quant-admin-token
```

所有密码明文写在 docker-compose.yml 中。

### 5.3 缺少数据库迁移工具

SQL 脚本放在 `modules/database/` 下手动管理（`01_init_schema.sql`, `02_additional_indexes.sql` 等），没有 Flyway 或 Liquibase。依赖人工记忆执行顺序。

### 5.4 JPA ddl-auto 使用 update

`application.yml:20`：

```yaml
jpa:
  hibernate:
    ddl-auto: update
```

`update` 模式在开发环境可用，但生产环境应使用 `validate` + 显式迁移脚本，防止意外的表结构变更。

### 5.5 Hibernate SQL 日志开启

```yaml
logging:
  level:
    org.hibernate.SQL: DEBUG
```

生产环境打印所有 SQL 会影响性能并泄露查询细节。

## 六、代码组织与可维护性 (P2)

### 6.1 项目模块结构不对称

根目录 `pom.xml` 只包含 `backend-java` 一个模块，而 `compute-python`, `web`, `database` 都在 `modules/` 下但不被父 POM 管理。这些模块之间没有统一的构建/测试/部署流程。

### 6.2 无 API 版本化

所有 API 路径为 `/api/xxx`，没有版本前缀（如 `/api/v1/xxx`）。未来 API 变更时会破坏现有客户端。

### 6.3 前端组件文件过多使用 Index.vue

14 个视图组件全部命名为 `Index.vue`，在 IDE 中通过 tab 标题无法区分：

```
dashboard/Index.vue
trading/Index.vue
account/Index.vue
chat/Index.vue
scheduler/Index.vue
settings/Index.vue
```

### 6.4 缺少请求日志和监控

没有 API 请求耗时统计、慢查询监控、打分任务执行时长追踪。`ScoringPropertiesBridge` 是静态桥接模式，不利于测试和配置热更新。

## 八、建议的修复顺序

```
第一轮（安全）:
  P0-2 API 权限控制 → P0-1 默认密码 → P0-3 CORS 限制

第二轮（正确性）:
  P1-1/P1-2 前端文件去重 → P1-3/P1-4/P1-5/P1-6 假数据修复

第三轮（测试）:
  P1-7 打分模块单元测试 → 技术指标验证 → 集成测试

第四轮（工程化）:
  P2-5 ddl-auto=validate → P2-4 数据库迁移 → P2-1 残留清理
  → P2-2 InfluxDB移除 → P2-3 密码外部化 → P2-6 API版本化
```
