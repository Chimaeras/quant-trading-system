# 阶段2：数据层修复与因子可用性缺陷

> 本文记录阶段2 中发现并修复的**结构性缺陷**、补数据的过程，以及仍未解决的缺口。
> 所有结论都区分「机制已验证」与「数据已到位」，不把两者混为一谈。

---

## 1. 修复的缺陷：三个基本面因子因接口未接通而**永久不可用**

### 1.1 缺陷原文

`FactorCalculator.compute()` 的签名**不接受**财务快照：

```java
public static Outcome compute(String stockCode, String exchangeType, String stockName,
                              LocalDate tradeDate, List<MarketData> bars, String industry)
```

而三个基本面因子的登记位置在这段代码里，**无条件**写死为不可用：

```java
reasons.put(FactorId.QUAL_ROE,     "NO_FINANCIAL_SNAPSHOT_SOURCE");
reasons.put(FactorId.QUAL_LEV,     "NO_FINANCIAL_SNAPSHOT_SOURCE");
reasons.put(FactorId.LIQ_CURRENT,  "NO_FINANCIAL_SNAPSHOT_SOURCE");
```

两个调用方（`UnifiedFactorMarketLoader` / `UnifiedFactorScoringService`）
**确实**从库里加载了 `stock_financial_snapshot`，但只能在 `compute()` **返回之后**
调 `applyFinancials(features, snap)` 补写值。而 `applyFinancials` 只写
`fv.setRoe(...)` 一类，**不登记 `available`**。

### 1.2 后果（两层，都真实）

1. **即使库里有财务数据也用不上**：`available` 集合里没有这三个因子，
   权重再高也会被 `RE_NORMALIZE_OVER_AVAILABLE` 剔掉。
   ⟹「综合」与「多维度」两个策略里声明的基本面权重（约 40%）**结构性空转**。
2. **归因被污染**：原因码写死为 `NO_FINANCIAL_SNAPSHOT_SOURCE`，
   即使快照存在、甚至已有非空 ROE，对外披露仍是"没有数据源"。
   这会让"到底是没数据还是没接线"无法区分——正是本轮要消除的盲区。

> 这是一个**接口设计缺陷**，不是数据缺失。补数据并不能解决它。

### 1.3 修法

给 `compute()` 加一个带快照的重载（旧 6 参签名保留并委托，行为不变）：

```java
public static Outcome compute(..., String industry,
                              com.quant.entity.StockFinancialSnapshot snapshot)
```

在快照非空时逐字段登记可用性，缺失时给**精确到字段**的原因码：

| 情形 | 可用性 | 原因码 |
|---|---|---|
| 快照存在且字段非空 | ✓ 加入 `available` | —— |
| 快照存在但字段为 null | ✗ | `NULL_ROE_IN_SNAPSHOT` / `NULL_DEBT_RATIO_IN_SNAPSHOT` / `NULL_CURRENT_RATIO_IN_SNAPSHOT` |
| 快照本身为 null | ✗ | `NO_FINANCIAL_SNAPSHOT_SOURCE`（保留原码） |

两个调用方改为把快照**传进** `compute()`，并删掉此后置的 `applyFinancials`
（`UnifiedFactorScoringService` 里那个已是死代码）。

### 1.4 回归测试

`FactorCalculatorTest` 新增 3 个测试，把该缺陷钉住：

| 测试 | 断言 |
|---|---|
| `financialSnapshotMakesQualityAndLiquidityFactorsAvailable` | 三因子可用、特征值正确、不再残留在不可用原因表 |
| `snapshotWithNullFieldsStillReportsPerFieldReason` | 部分字段 null 时**逐字段**给出精确原因码 |
| `legacyOverloadWithoutSnapshotKeepsFactorsUnavailable` | 6 参旧重载语义不变（仍是"确实无快照"） |

**测试结果：`FactorCalculatorTest` 14 个测试全通过**（原 11 + 新 3）；
连同 `UnifiedScoreReadServiceTest`(25) 与 `ScoringBeanWiringTest`(3) 共 **42 个全通过**。

## 2. 补数据：财务快照

上游：东方财富 F10 `RPT_F10_FINANCE_MAINFINADATA`。
字段映射（**每个字段都经真实响应核对**，非猜测）：

| 东财字段 | 含义 | → `stock_financial_snapshot` |
|---|---|---|
| `TOTALOPERATEREVETZ` | 营业总收入同比 % | `revenue_yoy` |
| `PARENTNETPROFITTZ` | 归母净利润同比 % | `net_profit_yoy` |
| `ROEJQ` | 加权 ROE % | `roe` |
| `ZCFZL` | 资产负债率 % | `debt_ratio` |
| `LD` | 流动比率 | `current_ratio` |
| `NOTICE_DATE` | 公告日 | `announcement_date` |

**PIT 纪律**：`announcement_date` 取公告日，配合
`FinancialSnapshotLoader` 的 `findByAnnouncementDateLessThanEqual`，
保证只有"公告日不晚于信号日"的财报才被使用 —— 否则就是未来函数。

`pb_ratio` **故意留空**：它需要信号日的行情价，本脚本不臆造。
PE/PB 的正源是 `market_data.pe_ratio / pb_ratio` 两根**行情列**（本库 100% NULL），
这是一个**独立且仍未解决**的缺口（见 §4）。

### 2.1 已验证的真实数据（样例，安银行 000001）

| 报告期 | 公告日 | ROE | 资产负债率 | 流动比率 |
|---|---|---|---|---|
| 2026-06-30 | 2026-08-15 | 5.22 | 90.91 | null |
| 2026-03-31 | 2026-04-25 | 2.83 | 90.98 | null |
| 2025-12-31 | 2026-03-21 | 9.15 | 90.70 | null |
| 2025-09-30 | 2025-10-25 | 8.28 | 91.02 | null |

- 报告期回溯到 **2021-12-31**（每股 12 期），公告日与真实披露节奏一致。
- `current_ratio` 对银行**正确为 null**（银行无流动比率口径），
  这正是逐字段原因码要保留的价值 —— 不能拿 0 冒充。

## 3. 补数据：行业分类

`stock_info.industry` 填充率 **0%**，直接导致：

- **行业中性化无法执行**（行业为空 → 中性化整体降级跳过）；
- 多维度打分里的 industry 比较项恒取默认值。

上游：东财 F10 `RPT_F10_BASIC_ORGINFO`，取 `EM2016`（东财/申万口径，形如
`食品饮料-饮料-白酒`）取**一级**行业写回 `stock_info.industry`；
同时保留 `INDUSTRYCSRC1`（证监会行业）备查。

> 注：`columns` 必须用 `ALL`。用字段白名单时该接口返回 0 行，
> 一度让我误判"接口不存在"——实际是字段名不在白名单里。

已验证样例：

| 代码 | `industry`（EM2016 一级） | 证监会行业 |
|---|---|---|
| 000001 | 金融 | 金融业-货币金融服务 |
| 000002 | 房地产 | 房地产业-房地产业 |
| 000004 | 信息技术 | 信息传输、软件和信息技术服务业-软件和信息技术服务业 |
| 000008 | 交运设备 | 制造业-铁路、船舶、航空航天和其他运输设备制造业 |

## 4. 仍未解决的缺口（**不得**当作已修）

| 缺口 | 现状 | 影响 |
|---|---|---|
| `market_data.pe_ratio / pb_ratio` | 256 万行 **100% NULL** | `VAL_EP` / `VAL_BP` 仍然必然不可用 |
| `MOM_5` / `MOM_120` | 计算器可算，但**5 个策略无一引用** | 全库 21 因子里只有 14 个真正参与打分 |
| 行业中性化 | 数据即将到位，但**引擎侧尚未启用**（需在阶段3 一并做） | d2 目标未完成 |
| `stock_info.list_date` | 276 只不可靠（多为北交所批次日期） | 60 日上市闸门对这些股票判断失真 |

**PE/PB 的可行补法**（尚未实施，需先决定口径）：
用 `Total_Equity_PK` 或 `BPS × 总股本` 推算市值，再以
`PB = 收盘价 / BPS`、`PE = 收盘价 / EPS(TTM)` 反向填充 `market_data`。
但这会**改写行情表**且引入 TTM 口径选择，属于需要单独评审的改动，
故本阶段**只记录，不实施**。
