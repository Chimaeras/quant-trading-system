# 实时量化监控交易系统后续实施计划 V2

日期：2026-08-19  
状态：批次 A、批次 B 核心功能已实施；批次 C-F 待实施；专项故障注入测试待补  
目标：将当前 Paper Watch 从“可受控联调的自动盯盘脚本”演进为“可长期运行、可恢复、可仿真、可审计的个人量化交易系统”。

## 1. 当前能力基线

| 领域 | 当前已有 | 当前等级 |
|---|---|---|
| 股票范围 | Java 主数据分页加载沪深北全市场 | 已具备基础能力 |
| 实时行情 | 全市场批量轮询；信号后用妙想补执行级行情 | 准实时、非流式 |
| 分钟 bar | 内存聚合固定周期 OHLCV，只用已收盘 bar | 可用但不可恢复 |
| 策略 | MA_CROSS / MACD / BOLL 三选一 | 示例策略级 |
| 买卖信号 | 柜台持仓外置，买卖均可生成限价意图 | 已形成基本闭环 |
| 前置风控 | 行情新鲜度、涨跌停、资金、仓位、持仓数、冷却、日限额、重复委托等 | 基础安全级 |
| 模拟下单 | 可向妙想模拟盘提交；live 有多重开关 | 受控联调级 |
| 未知提交 | UNKNOWN_SUBMIT 冻结并等待柜台委托核验 | 已具备关键安全能力 |
| 状态持久化 | 交易计数、冷却、未知提交写 state.json | 局部持久化 |
| 监控 | JSONL 事件、tick 快照、只读 API、Vue 面板 | 开发监控级 |

## 2. 核心判断

当前系统离“真实量化系统”最远的不是下单 API，而是下面四个运行时闭环：

1. **数据闭环**：分钟历史、实时快照、缺口检测和策略状态不能可靠跨重启恢复。
2. **订单闭环**：提交之后缺少本地 OMS 状态机、部分成交、撤改单、成交回报和资金占用生命周期。
3. **仿真闭环**：dry-run 只生成意图，没有跨轮次、跨交易日的虚拟资金、持仓、委托和成交。
4. **运维闭环**：没有单实例租约、心跳、外部告警、进程守护、数据保留和灾难恢复演练。

因此后续应先建设运行底座，再增加复杂策略。否则策略越多，错误下单和不可复盘的概率越高。

## 3. 缺失功能与逻辑

### 3.1 P0：无人值守前必须补齐

#### RT-01 单实例运行与进程租约

现状：没有进程锁或 leader lease。两个 `paper.cli watch --live` 进程可能同时读取相同账户快照并竞争提交；仅依赖柜台活动委托不能消除并发窗口。

需要：

- 启动时获取带 owner、PID、host、started_at、heartbeat_at 的交易引擎租约。
- 租约有效时第二实例只能启动为只读/dry-run，不能进入 live。
- 心跳超时后的接管必须先执行账户和订单全量对账。
- Windows 异常退出、PID 复用和时钟回拨均要有测试。

验收：并发启动两个 live 实例，实际 `trade_calls` 总数仍只能来自一个实例。

#### RT-02 持久化运行库

现状：bar、forming bar、策略价格序列、最近行情和订单生命周期主要在内存或分散 JSON 文件中。

建议：新增 `WatchStore` 抽象，个人单机版先实现 SQLite WAL；禁止业务代码直接依赖 SQLite，以便后续切换 MySQL/PostgreSQL。

最小表：

- `engine_lease`：单实例租约和心跳。
- `closed_bar`：代码、周期、开始时间、OHLCV、source、quality_status。
- `forming_bar_checkpoint`：当前桶快照及累计量基线。
- `strategy_state`：策略版本、参数哈希、最近已处理 bar、warmup 状态。
- `local_order`：本地订单、柜台订单号、幂等键和状态。
- `fill`：成交数量、价格、费用、时间。
- `account_snapshot`：余额、持仓、活动委托及快照一致性标记。
- `cycle_metric`：覆盖率、延迟、缺失、信号、风控和订单统计。

要求：事务、唯一键、schema migration、原子提交、备份与损坏恢复测试。

#### RT-03 bar 与策略状态恢复

现状：FULL 模式未持仓股票每天从零累计。MA20 + 5 分钟策略约需 100 分钟才具备信号能力；进程重启再次失忆。

需要：

- 每根已收盘 bar 幂等入库，唯一键为 `(code, period_min, start_ts)`。
- 开盘前从运行库加载每只股票所需的最近 N 根 bar。
- 保存最后已处理 bar 时间，重启时不得重复触发同一交叉信号。
- forming bar 恢复必须区分完整桶与启动残段，缺口不能合成假 bar。
- 跨日保留历史序列，但显式处理隔夜跳空和集合竞价。
- 首次部署历史不足时只允许 WARMUP，不得用日线或前收盘价伪造分钟 bar。

验收：进程在 10:17 被强制终止并于 10:19 重启，10:20 后的 bar、信号和成交量增量与不中断运行一致。

#### RT-04 本地 OMS 订单状态机

现状：柜台订单状态保留原始枚举；watch 只记录 SUBMITTED/UNKNOWN/REJECTED，没有完整生命周期。

需要建立：

`CREATED → SUBMITTING → SUBMITTED → PARTIAL → FILLED`  
以及 `CANCEL_PENDING → CANCELLED`、`REJECTED`、`UNKNOWN`、`EXPIRED`。

核心规则：

- 每个订单生成稳定 `client_order_id` 和幂等指纹。
- `trade` 仍禁止网络错误自动重试；先用订单指纹和柜台订单查询消解 UNKNOWN。
- 周期性同步部分成交、剩余数量、均价、费用和最终状态。
- 订单状态只能按允许路径单向迁移，异常倒退必须告警并冻结。
- 本地状态落库失败时不允许提交下一单。
- 活动委托资金和仓位承诺必须来自 OMS，而不是临时列表。

#### RT-05 订单超时、撤单与撤改

现状：有人工 `cancel` 客户端，但 WatchLoop 不管理超时活动委托。

需要：

- 买入、卖出分别配置订单 TTL。
- TTL 到期后先查柜台最新状态，再决定撤单；撤单请求也按 UNKNOWN 处理。
- 撤改必须是“旧单确认撤销后才发新单”，禁止并行产生双份委托。
- 临近午休、收盘、涨跌停和行情失效时使用不同策略。
- 默认不实现追单；第一阶段只做安全撤单，撤改需单独开关。

#### RT-06 账户级止损和紧急停止

现状：已有静态仓位/现金/数量风控，但没有基于当日权益变化的动态风控。

需要：

- 当日已实现亏损、浮动亏损、总权益回撤上限。
- 连续拒单、连续行情缺失、连续对账失败、延迟超限触发 kill switch。
- kill switch 状态持久化，重启不能自动解除。
- “禁开仓”“只允许减仓”“完全禁止下单”三级状态。
- 手工紧急停止文件/API；控制 API 必须鉴权、审计且默认仅本机。

#### RT-07 启动前就绪检查

live 启动前必须一次性验证：

- 交易日历、北京时间和时钟偏差。
- 股票主数据数量与市场覆盖。
- 分钟预热覆盖率。
- 行情延迟与页面完整性。
- 余额/持仓/订单三查询一致。
- 本地 OMS 与柜台对账无 UNKNOWN。
- 引擎租约唯一。
- 数据库可写、磁盘空间和日志目录可用。

任一硬检查失败只允许 dry-run。

### 3.2 P1：让“全市场实时监控”真正可持续

#### MD-01 行情源抽象和服务等级

现状：业务代码直接依赖妙想查询与东方财富批量 HTTP。

需要统一接口：

```text
MarketDataProvider
  snapshot_all(universe) -> BatchQuoteResult
  snapshot_execution(code) -> ExecutionQuote
  history(code, period, limit) -> ClosedBars
  health() -> ProviderHealth
```

要求：

- 明确分钟级系统和 tick/盘口系统的边界。
- 当前公开 HTTP 源只能定位为研究/筛选源，不声明生产 SLA。
- 如目标是盘口级真实交易，必须接入有授权、有推送、有序列号的数据源。
- 主源/备源切换不能混用不同复权、单位和时间口径。

#### MD-02 两级全市场流水线

推荐架构：

1. Level 1 全市场扫描：行情质量、停牌、成交额、流动性、板块、涨跌幅和粗筛。
2. Level 2 活跃池：全部持仓、全部活动委托、候选 Top-N，维护完整分钟序列和执行级行情。

好处：既能覆盖所有股票，又不需要对数千只股票逐只调用昂贵接口。

需要记录：全市场总数、返回数、可交易数、策略 ready 数、Level 2 数和各阶段淘汰原因。

#### MD-03 行情质量与缺口检测

- 批次 ID、源时间、接收时间和处理时间分开记录。
- 代码缺失、跨页重复、快照倒序、成交量回退、价格突变和未来时间戳检测。
- 交易时段内连续 N 轮缺失触发证券禁用或全局降级。
- 对持仓和活动委托股票使用更严格的延迟阈值。
- 午休、集合竞价、临时停牌和收盘后的状态不能都归类为零成交量。

#### MD-04 证券交易规则主数据

需要为每只证券提供按交易日生效的规则：

- 市场、板块、ST/风险警示、上市天数、停复牌、退市整理。
- 价格最小变动单位、涨跌幅制度、无涨跌幅限制日、价格笼子。
- 买入单位、卖出零股处理、T+1/T+0 属性。
- 规则版本和来源必须随订单审计快照落盘。

### 3.3 P1：真正的模拟交易系统

#### SIM-01 内部 Paper Broker

现状：dry-run 不会形成可跨周期持有的虚拟账户；妙想模拟盘不可用时无法独立仿真。

需要实现 Broker 接口的内部模拟版本：

- 现金、冻结资金、持仓、今日买入、可卖数量。
- 限价单、撤单、部分成交和订单生命周期。
- 手续费、印花税及可配置费用策略。
- 成交延迟、滑点、成交量参与率和无法成交原因。
- 日终结算、T+1 可卖转换、权益曲线和持仓成本。
- 所有状态持久化，重启后继续同一个 simulation_session。

第一阶段基于分钟 bar 做保守撮合；没有盘口时不得宣称模拟了排队位置。

#### SIM-02 撮合模型

建议分三档：

- `CONSERVATIVE_BAR`：买单限价高于 bar low 不代表必成，需额外成交概率/成交量约束。
- `TOUCH_FILL`：价格触达即成交，仅用于乐观对照。
- `NEXT_BAR`：信号在 bar 收盘产生，最早下一根 bar 才能成交，避免未来函数。

每次仿真必须保存撮合模型和参数哈希，确保回放一致。

#### SIM-03 双通道运行

- `SHADOW`：只产生信号与模拟成交，不访问外部 trade。
- `INTERNAL_PAPER`：内部账户完整仿真。
- `EXTERNAL_PAPER`：妙想模拟盘真实请求。

同一策略可同时跑 shadow 与 external paper，用于比较信号价、委托价、成交价和滑点，但两个通道订单必须完全隔离。

### 3.4 P1：风控真实性

#### RISK-01 流动性和订单容量

- 最近 N 日平均成交额和当前分钟成交额下限。
- 单笔订单金额不得超过近期成交额或当前 bar 成交量的配置比例。
- 极低价、高价、异常波动、新股和风险警示股票单独限制。
- 买入限价偏离最新价、卖一价或基准价超过阈值时拒绝。

#### RISK-02 组合暴露

- 行业、板块、市场和策略维度的仓位上限。
- 单一风险因子和高相关持仓聚集度。
- 当日换手率、总委托金额、撤单率和拒单率限制。
- 待成交买单计入潜在持仓；待成交卖单不能提前释放现金。

#### RISK-03 退出规则

当前卖出主要依赖策略反向交叉，需要增加独立于入场策略的退出引擎：

- 固定/ATR 止损。
- 止盈和移动止盈。
- 最大持仓时间。
- 信号失效退出。
- 大盘或行业风险退出。
- 尾盘是否强制减仓按策略配置。

退出信号仍必须经过可卖数量、跌停、活动卖单和行情质量闸门。

### 3.5 P2：策略从示例升级为可验证系统

#### STR-01 策略注册与多策略仲裁

- 策略具有唯一版本、参数哈希、所需字段、warmup 数和适用市场。
- 同一股票多个策略冲突时由组合层仲裁，不允许按代码遍历顺序决定。
- 信号对象包含强度、有效期、目标仓位、退出条件和证据快照。
- 订单数量由 Portfolio/Sizer 统一决定，策略不直接决定股数。

#### STR-02 接入现有 Java 评分与研究成果

项目已有多维打分、概率、T1 候选、行业和流动性能力，但 Paper Watch 当前主要只使用简单分钟技术策略。

建议：

- 日前候选与概率作为 Level 1 先验。
- 盘中分钟信号作为入场时机，不独立承担选股。
- 持仓退出不依赖候选仍在榜。
- 每笔订单记录候选版本、模型版本、特征快照和盘中信号版本。

#### STR-03 回测、仿真、Paper Live 同源

- 统一 Signal、Risk、Sizer、FeePolicy 和 ExecutionModel 接口。
- 相同策略在历史回放、内部 Paper、外部 Paper 中使用同一核心代码。
- 禁止 live 专属策略逻辑无法被历史回放。
- 上线门槛包括 walk-forward、样本外、成本后收益、最大回撤和稳定性。

### 3.6 P2：监控、审计和运维

#### OBS-01 可扩展事件存储

现状：全市场逐股 JSONL 事件和每轮完整 universe 会快速膨胀；监控 API 多处顺序扫描文件。

需要：

- 最新行情使用覆盖写的 `latest_quote` 表/快照，不为每只股票每轮追加普通 QUOTE 事件。
- 事件流只保存状态变化、异常、有效信号、风控和订单生命周期。
- 分区、索引、轮转、压缩和保留期。
- tick artifact 只保存 universe_hash 和摘要，完整主数据按版本单独保存一次。

#### OBS-02 指标与告警

指标至少包括：

- 行情覆盖率、策略 ready 覆盖率、行情年龄 P50/P95/P99。
- 每轮耗时、单阶段耗时、遗漏 bar 和积压轮次。
- 信号/风控/订单漏斗、拒单率、撤单率、UNKNOWN 数。
- 账户权益、当日盈亏、回撤、仓位和风险暴露。
- 数据库、磁盘、API 配额和进程心跳。

STOP_RUN、UNKNOWN、低覆盖、持久化失败和租约丢失必须支持外部通知；控制台日志不够。

#### OBS-03 监控面板

新增页面/区域：

- 引擎健康和租约 owner。
- 全市场漏斗与缺失代码。
- 持仓、资金、盈亏和风险预算。
- 订单 blotter、部分成交、剩余数量和订单时间线。
- kill switch 状态及只减仓模式。
- 策略版本、预热覆盖和信号证据。

控制操作与只读监控分离；任何控制动作必须二次确认和审计。

#### OPS-01 运行编排

- 开盘前启动并执行预热/readiness。
- 午休不浪费外部配额，但维持心跳和订单对账。
- 收盘后停止新信号、完成对账、日终结算和报告。
- 服务管理器/任务计划自动拉起，异常重启前先检查租约和 UNKNOWN。
- 优雅退出不默认全撤，但必须落盘最终状态并明确列出未完成订单。

## 4. 推荐实施顺序

### 批次 A：耐久运行底座（建议下一步先做）

范围：RT-01、RT-02、RT-03、RT-07 的本地部分。

主要交付：

1. `WatchStore` 接口、SQLite WAL 实现和 migration。
2. 单实例租约与心跳。
3. closed/forming bar 检查点、跨重启恢复和信号去重。
4. 启动 readiness 报告；live 硬阻断，dry-run 可降级。
5. 旧 JSON state 一次性迁移；迁移后保留只读备份。

预计涉及：

- 新增 `paper/watch/store.py`、`paper/watch/migrations/`、`paper/watch/lease.py`、`paper/watch/readiness.py`。
- 修改 `bar_store.py`、`signal_adapter.py`、`state.py`、`loop.py`、`cli.py`、`config.py`。
- 增加崩溃恢复、双实例竞争、跨日和重复 bar 测试。

批次 A 完成后，才解决“开盘预热”和“进程重启不失忆”的根问题。

### 批次 B：OMS 与内部仿真

范围：RT-04、RT-05、SIM-01、SIM-02、SIM-03。

主要交付：持久化订单状态机、成交表、持续对账、安全撤单、内部 Paper Broker、三种运行模式。

验收：同一录制行情重复回放两次，订单、成交、费用、持仓和权益结果完全一致；在任意状态强制重启都不重复发单。

### 批次 C：全市场数据流水线

范围：MD-01 至 MD-04、OBS-01 的行情部分。

主要交付：行情源适配层、Level 1/Level 2、质量检测、规则主数据、latest snapshot。

验收：完整交易时段持续运行，覆盖率和延迟达到预先约定的 SLA；持仓和活动委托标的不得出现未告警的数据空窗。

### 批次 D：动态风控和退出引擎

范围：RT-06、RISK-01 至 RISK-03。

主要交付：权益/回撤 kill switch、流动性容量、组合暴露、独立退出策略、只减仓模式。

### 批次 E：策略和研究同源

范围：STR-01 至 STR-03。

主要交付：策略注册、组合仲裁、Java 选股先验接入、统一回放/仿真/live 接口和上线门槛。

### 批次 F：监控与生产化运维

范围：OBS-02、OBS-03、OPS-01。

## 5. 首批建议范围

建议下一次实际修改只执行“批次 A”，不要同时改策略和 OMS，原因是：

- 它先消除多进程重复下单和重启失忆两个最高风险。
- 它为 OMS、仿真和可扩展监控提供统一事务存储。
- 改动可用纯离线测试完整验证，不需要立即触碰外部模拟盘。

批次 A 明确不做：

- 不自动调用 trade/cancel。
- 不改变 MA/MACD/BOLL 信号公式。
- 不切换外部行情源。
- 不删除现有 JSON artifacts；仅增加持久化底座并保持兼容。

## 6. 批次 A 验收清单

1. 两个进程竞争时只有一个获得 live lease。
2. lease 丢失后的当前轮次在任何 trade 之前停止。
3. 5 分钟 bar 重启恢复后与连续运行 OHLCV 完全一致。
4. 已处理 bar 不会在重启后重复产生买卖信号。
5. 前一交易日最后 N 根 bar 可用于次日 warmup，且不生成伪造 bar。
6. SQLite 事务中断不会留下半条 state/order/bar。
7. 数据库损坏、只读或磁盘满时 live 启动失败。
8. 旧 state.json 可迁移；损坏旧状态仍 fail-closed。
9. 现有 Python 全量测试、Java 测试和前端构建保持通过。
10. 完成离线故障注入测试后，才允许进入新的全市场 dry-run。

## 7. 需要用户确认的架构选择

### 选择 1：行情目标

- 推荐：先做“分钟级全市场 + 秒级活跃池”，适配现有 5 分钟策略。
- 更高目标：tick/盘口级全市场，需要有授权的推送行情源，工作量和基础设施明显增加。

### 选择 2：运行库

- 推荐：个人单机阶段使用 SQLite WAL + Repository 抽象，部署简单、事务可靠。
- 备选：直接使用现有 MySQL，便于 Java/Python共享，但需要连接池、数据库依赖和更严格的部署管理。

### 选择 3：模拟方式

- 推荐：内部 Paper Broker 与妙想模拟盘并存；内部用于确定性回放，妙想用于外部链路联调。
- 仅妙想：实现较少，但无法离线重放、故障注入和稳定验证撮合逻辑。

## 8. 完成定义

即使全部批次完成，也只能称为“具备生产化工程结构的个人量化 Paper 系统”。是否具备真实交易价值仍取决于：

- 行情和交易接口的授权、稳定性与 SLA。
- 策略样本外、成本后和多市场状态下的有效性。
- 持续 Paper Live 运行数据、故障演练和人工审核。
- 在切换任何真实资金接口前重新完成独立安全审查。
