## 三、已验证但**判定不修改**（后续勿再报，属重复返工）


1. **"外部 HTTP 被包在 `@Transactional` 内会占满连接池"（代理 P1）→ 判废，非缺陷。**
   `HistoricalDataService`（3 处）、`IndexDataService.fetchAndPersist`、`TradingCalendarService.deriveFromShIndex` 共 5 个入口确实在 `@Transactional` 方法内发 HTTP，但**都是先拉网络、后碰数据库**
   （`HistoricalDataService.java:103/193/722`、`IndexDataService.java:83`、`TradingCalendarService.java:76`，其后的首个 DB 访问分别在 `:140`、`:201+`、`:731`、`:87`、`:80`），
   而 Hibernate 6 默认 `DELAYED_ACQUISITION`（首个 JDBC 语句才向 Hikari 借连接）。故网络等待期间**并未持有连接**，事务虽长但为空载。
   真正会占连接的写法是"事务内先查库、再发 HTTP"，本仓未出现。
2. **`BacktestTurnoverService` 换手率分母固定 topN（代理 P2）→ 判废。** 该口径在前序轮次已核验判定正确（分母=topN、除零有保护），不再更改。
3. **`watch/loop.py` 的 `frozen_codes`（代理 P3"守卫不可达"）→ 确认为冗余而非缺陷，不修改。**
   `frozen_codes` 是单轮局部集合（`loop.py:2034`），检查（`:2117-2120`）永远早于写入（`:2336-2337`），故该分支不可达；但 `UNKNOWN_SUBMIT` 同时置 `self._live_halted = True`（`:2314-2316`），后续候选已被 `LIVE_HALTED` 拦截，
   即同一保护已由更强的实例级开关承担。删除或改持久化都不改变可观测行为，故保留现状并在此登记，避免下轮重复"修"。
4. 已查、无问题的维度：JWT 算法混淆与密钥长度（仅 `SecretKey` + `parseSignedClaims`）、userId 维度越权（`UserIdResolver` 鉴权开启时强制取 `AuthContext`，`requireSession` 按账户校验归属）、
   拦截器路径匹配与 CORS（显式来源 + credentials，无通配）、线程池有界性与 `@Async` 回退、异常信息泄漏与吞栈、
   `HashMap`/`SimpleDateFormat` 跨线程共享、除法零/空守卫、Comparator 契约、`BigDecimal.equals`、金额 `double` 相等比较。

1. **`FactorResearchService` 全市场区间行情加载**（`:915-916`/`:931-932`/`:499-500`）：区间内全部 qfq+raw 实体水合后再内存过滤，长区间内存压力大。修法需新增"按 stock key 集合 + 分片"的仓储查询并改造调用链，属重构；另需评估是否引入区间跨度上限。
2. **`FinancialSnapshotLoader` 全表/全历史加载**（`:24-42`）：需以窗口函数在 DB 层取每股票最新报告期（原生 SQL），并处理 MySQL 8 兼容与方言。
3. **`DailyReportService.ensureReport` 并发首建兜底失效**（`:283-292`）：`save` 冲突后在同一事务内重读，事务已被标记 rollback-only，真并发下两条请求都可能 500。修法需把"首建 + 冲突后重读"放入 `REQUIRES_NEW` 独立事务（并保证 hash 校验在新事务内完成），涉及取数逻辑重排。
4. **打分结果头/明细非原子写入**（`OversoldReboundScoringService.java:380/387/397/403`、`StockSelectorService.java:376-382`）：头先置 SUCCESS、再删旧明细、再写新明细，且三者在不同事务中；读取窗口内可能见到"SUCCESS 空明细"，写入异常会留下永久中间态。修法需统一事务边界与终态时序（且要兼顾既有 `ProgressiveResultWriter` REQUIRES_NEW 的渐进写语义）。
5. **`MarketDataRepository` 的 `concat(stockCode,'|',exchangeType) in :keys`**（`:104-112`）：函数包裹列导致索引失效。改法（拆成两列 IN 或按 key 分片）需核对调用方过滤语义与结果集等价性，当前调用规模可控。
6. **前向收益扩窗用日历天（`plusDays(holding*2)`）而非交易日**（`ScoringBacktestService.java:141`、`FactorResearchService.java:148/205`）：跨春节/国庆等长休市时末端信号可能被 `SKIP_BEYOND_CALENDAR` 静默丢弃。修法建议改为按交易日历推进或"留量 + 断言窗口内交易日数"，需同步评估对既有回测样本量的影响。
7. **鉴权关闭 + prod/docker profile 不 fail-fast**：本轮只加醒目 WARN。硬失败会打断现存以 `AUTH_ENABLED=false` 运行的部署（属运维决策），需先确认部署口径再改。
