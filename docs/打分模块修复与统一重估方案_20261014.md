## 0. 摘要

### 0.1 一句话结论

**当前 5 套打分在数据层已经"空心化"：所有基本面与行业维度都在拿常数打分，分数的全部区分度只来自技术面一个维度。**
所以要做的不只是"改公式"——得先让因子**有数据可用**、**在同一个截面上可比**，然后才谈权重。统一引擎正是为此服务的：它把"因子的取值"与"因子在某个策略里的权重"彻底分开。

### 0.3 对上轮结论的更正（必须记录）

我上一轮曾写：

MULTI_DIM 五维度的实际取值（用库内数据验证）：

| 维度 | 实际表现 | 证据 |
|---|---|---|
| tech 技术面 | **唯一变量维度** | — |

### 0.4 好消息（不该被忽略）

- **横截面数学工具箱已经建好了**：`CrossSectionFactorMath` 有 winsorize(2.5/97.5)、稳健 Z（median+MAD，clip ±3）、按行业分组 Z（组内 <5 回退全截面）、百分位得分（平均秩，处理并列）。质量很好，**但没有被 5 套打分中的任何一套使用**（只有 Codex 路径用了其中的 `percentileScores`）。
- **行业中性化已经有了**：`CrossSectionNeutralizer` 做 `winsorize → OLS(x ~ 1 + lnMV + 行业哑变量, ridge=1e-4) → robustZ(MAD, clip ±3)`。这是学术标准做法。
- **`PointInTimeUniverseProvider` 已被 5 套服务全部注入**，PIT 股票池的地基在。
- **成本口径被测试钉死**（`FactorResearchEngineCostBasisTest`：乘性 15bp/腿）。
- **失败披露做到了**：`ScoreReadAvailability` 会区分 `OK/STALE/EMPTY`；`data_quality` 会标记 `FULL/PARTIAL_FUNDAMENTALS/TECHNICAL_ONLY`；`shortHorizonValidation` 自己判 `t3_effective=false`、`confidence=低`。

**结论：这个项目的"诚实度"高于它的"有效性"。** 修复方向因此很清楚——把已有的正确工具接上，而不是重写。

## 2. 目标架构：一次计算 + 五份策略声明

### 2.1 核心设计原则

1. **因子的"取值"与"在某策略里的权重"必须分离。** 同一个 RSI 因子在趋势策略里加分、在超跌策略里反向加分——这没问题；但**它必须是同一个数**。当前问题是两处各算一遍，阈值还不同。
2. **一切输出在横截面上可比。** 统一输出截面分位 [0,1]（或 ×100），彻底消除"42.56 vs 67.17"。
3. **行业不做加分，只做中性化。** 把行业作为哑变量从因子值里回归掉，而不是把行业偏好加到分数上。
4. **每个分数必须可归因、可复算。** 明细要落库，且带齐"截面"信息（截面有多少只股票、什么过滤条件）。
5. **缺数据必须显式，不能静默填 0 或填中性值。**

### 2.2 分层结构

```
┌─ L0 原始数据（本次不改）─────────────────────────────┐
│  market_data(K线) / stock_info / stock_financial_snapshot │
│  + PointInTimeUniverseProvider（已有）                    │
└──────────────────────┬───────────────────────────────┘
                       ↓  每只股票只加载一次
┌─ L1 FeatureVector（新增）────────────────────────────┐
│  价量特征（纯个股、无截面依赖）：                          │
│    ret1/5/20/60/120, ma5/10/20/60/120, rsi14, macd,      │
│    kdj, bias5, turnover, volumeRatio, avgAmount20,        │
│    vol20, mdd60, amplitude, 连续量能, 均线粘合/发散          │
│  估值/财务特征（来自 PE/PB/财报，缺则为 null）：            │
│    pe, pb, roe, debtRatio, currentRatio                   │
│  ★ 关键：缺失值就是 null，绝不填 0 或中位数                  │
└──────────────────────┬───────────────────────────────┘
                       ↓  整个截面一次性计算
┌─ L2 FactorLayer（新增）──────────────────────────────┐
│  统一管道：winsorize(2.5/97.5)                            │
│           → 中性化（lnMV + 行业哑变量，行业缺失则只中性化市值）│

│  输出：compositeScore = Σ(w_i · factor_i)，再取截面分位       │
└──────────────────────┬───────────────────────────────┘

┌─ L4 输出契约（扩展）─────────────────────────────────┐

│  + factor_contributions JSON（逐因子取值与贡献，可归因）      │
│  + universe_fingerprint（截面指纹，保证分数可比性可追溯）      │
└──────────────────────────────────────────────────────┘
```

### 2.4 五个策略变成声明

```java
// 示意：CLASSIC_SELECTOR
StrategyConfig.builder("CLASSIC_SELECTOR", "unified_classic_v2")
    .minBars(70)
    .weights(Map.of(
        "TREND_MA",   0.35,   // 原 trend 维度
        "MOM_20",     0.15,   // 原 momentum 维度（拆开 RSI 与 MACD）
        "MACD_HIST",  0.05,
        "AMT_20",     0.10,   // 原 volume 维度
        "VOL_RATIO",  0.10,
        "VOL_20",    -0.15,   // 原 riskPenalty（负向）
        "MDD_60",    -0.10))
    .gates(g -> g.minAvgAmount(30000).ma20AboveMa60().minBars(70))
    .build();
```

**关键收益：5 个策略共用同一份 `TREND_MA` 取值。** 现在 TREND 与 OVERSOLD 对同一个"趋势"给出的是两个不相干的数（`trend_score` 在 TREND 里 0~30、在 OVERSOLD 里 20~40）。

| # | 决策点 | 我的建议 | 理由 |

## 5. 验收标准（可执行、可证伪）

**本方案的成败不看"分数好不好看"，只看下面 6 条能否被独立验证。**

| ID | 验收项 | 判定方法 | 通过标准 |
|---|---|---|---|
| **V-1** | 因子取值不因策略而变 | 同一 `(trade_date, stock_code)` 在 5 个策略下取同名因子值 | 完全一致（同一份 `FeatureVector`） |
| **V-2** | 缺失数据不再伪装成数值 | 查 `factor_contributions` 中 `VAL_EP`/`QUAL_ROE` 等 | 在 `pe_ratio` 全 NULL 的前提下必须是 `null`，**不得**是 60.0 或 0.0 |
| **V-3** | 分数尺度可比 | 5 个策略同一日 `final_score` 分布 | 全部落在 [0,100] 且分位分布近似均匀（KS 检验或直方图目视） |
| **V-4** | 分数可归因、可复算 | 取任意一行，用 `factor_contributions` 的 `weight × pct` 求和 | 与 `final_score` 差异 < 0.01 |
| **V-5** | `total_score` 可由子项还原 | 对 `stock_trend_score` 全部行验证 | 12 子项之和 = `total_score`（容差 0.01） |
| **V-6** | ST / 不可交易标的不再出现 | 全库扫描 `stock_name LIKE '%ST%'` | **0 行** |

**关于"有效性"（预测力）的验收必须与"正确性"分开**：
- 本方案**不承诺**提升 Rank IC。原因：目前的实证基础是"4 个有效截面日、0 次校准、0 次候选核销"。
- 统一引擎的价值是让验证**第一次成为可能**：一个分数、一组因子、一套口径、可逐日复算。
- 建议的验证路径：统一引擎 → 逐日重放（QP-007，独立工程）→ ≥60 个截面的 Rank IC + Newey-West HAC t 值 + 分组单调性 + 扣 30bp 成本后的超额。

**新增文件**（全部在 `com.quant.service.scoring.factor` 包下，与既有打分服务隔离，不影响旧路径）：

| 文件 | 层 | 职责 |
|---|---|---|
| `FeatureVector.java` | L1 | 单只股票的原始特征向量，**缺失即 null** |
| `FactorId.java` | L2 | 因子注册表：21 个因子 + `minBars` + `isFundamental()` |
| `FactorCalculator.java` | L1 | `List<MarketData>` → `FeatureVector` + 可用性 + 不可用原因 |
| `CrossSectionNormalizer.java` | L2 | winsorize → 中性化 → 稳健Z → 百分位，**复用**既有数学工具 |
| `StrategyDefinition.java` | L3 | 声明式策略配置（权重/闸门/缺数据策略） |
| `StrategyCatalog.java` | L3 | 5 个策略的具体配置（含权重来源映射表） |
| `UnifiedFactorScoringEngine.java` | L4 | 组装 + 逐因子归因 + 资格判定 + 最终排名 |

**关键设计决定（与 §4 的 D-1..D-6 对应）**：

1. **方向不进因子层**（D-2）。波动率/回撤/资产负债率的"越大越差"用**负权重**表达，
   因子取值本身在所有策略里完全一致。这是 V-1 验收项，已用测试锁定：
   同一个因子在 5 个策略下的百分位序列逐元素相等。
2. **缺失即 null，绝不填中性值**（D-1）。`FeatureVector.peRatio()` 在 PE 缺失时返回
   `null` 而不是 0 或 60；`CrossSectionNormalizer` 对不可用因子返回 `null` 百分位
   **且不参与排名**（若把 null 当 0 参与，会把"没数据"排成"最差"）。
3. **分数尺度统一**（D-3）。`factorScore` 是加权和，`finalScore` 是它的**横截面百分位**。
   测试断言 20 只互异股票的 `finalScore` 跨度必须恰好 = 100.0
   ——对比当前 MULTI_DIM 实测 span 仅 **4.48**、COMPREHENSIVE 仅 **2.54**。
4. **缺数据必须可归因**（D-1 延伸）。每只股票输出 `availableWeightRatio`
   （可用归一化权重占比）与逐因子 `unavailableReason`；
   低于 `minAvailableWeightRatio` 时**拒绝打分并说明原因**，而不是拿残缺因子凑一个分数。

**复用而非重写**：`CrossSectionFactorMath`（winsorize / 稳健Z / 百分位）与
`CrossSectionNeutralizer`（OLS 中性化）本身实现良好，问题只是**5 套打分没有任何一套在用**
（仅 Codex 路径用了 `percentileScores`）。本批把这条管道真正接上，
未新增任何统计学实现。

#### 8.8.5 重复运行治理：找到 41% 重复率的机制并修掉

核验报告记录了「5972 条观测 → 3525 条唯一 `(strategy, date, stock)`，重复率 41.0%」，
以及 `authoritative_run` / `authority_source` 对全部 72 条 `selector_result` 均为 NULL。
本批在追查 `request_fingerprint` 时找到了**确切机制**，它不是"没人管"，而是逻辑分支漏了一条。

**机制**：`persistUnifiedInTransaction` 每次都生成新的 `resultId`
（`"US" + System.currentTimeMillis() + random`），而"是否已存在同请求结果"的检查
只写在**调用方传入固定 `resultId`** 的分支里。于是：

- 走"生成新 resultId"的主路径 → `request_fingerprint` 被**写入但从不用于查重**；
- 同一请求执行两次 → 必然产生两条结果行 → 明细翻倍。

**佐证**：任务路径 `createTask` 是**正确**的——它用
`findFirstByStrategyAndRequestFingerprintOrderByCreatedAtDesc` + `SUCCESS` 做去重
（`UnifiedScoringService:212`）。所以这是"一条路径做了、另一条漏了"，而非设计缺失。

**修法**：
1. `SelectorResultRepository` 新增
   `findFirstByStrategyTypeAndRequestFingerprintAndTradeDateAndRunStatusOrderByCreatedAtAsc`。
2. `persistUnifiedInTransaction` 在生成新 `resultId` **之前**，按
   `(策略 + 指纹 + 交易日 + SUCCESS)` 查找既有结果；命中则**直接复用其 resultId，不新建行**。
3. 新增入参 `dedupe`（默认 `true`）；排查/压测需强制重算时传 `dedupe=false`。
4. `persistUnified` 返回类型改为 `record PersistOutcome(String resultId, boolean deduplicated)`，
   把"本次是否复用"这一事实显式回传，响应新增 `deduplicated` 与 `deduplicated_note`。

**为什么必须带 `tradeDate` 查询**（这是最容易写错的地方）：
指纹由请求参数构成，**不含交易日**。若只用 `(策略, 指纹)` 查找，
10-14 的运行会被误判成"10-13 已经跑过"而直接复用旧结果——
表现为"换了日期却拿到旧数据"，且不会报错。已用
`lookupIsScopedToTheTradeDateSoDifferentDaysAreNotConfused` 钉住这条。

**只复用 `SUCCESS`**：`RUNNING` / `PARTIAL` / `FAILED` 必须重新计算，
否则一次失败会永久卡住该请求。

**为什么复用而不覆盖**：`persistUnified` 已有 `findStockKeysByResultId` 跳过既有明细的逻辑
（断点续跑用），因此"重写同一 resultId"是设计上支持的。但复用更保守：
不改变任何既有行，只避免新增。代价是"结果可能来自参数等价的更早一次运行"——
在参数等价的前提下这是可接受的。

**新增 4 个测试**（`UnifiedScoringServiceDedupeTest`）：
同请求复用且**绝不** `save` 新行、`dedupe=false` 强制落库、
非 SUCCESS 不复用、查询必须带交易日。

> **尚未做**：对**历史已有**的重复行做清理或标注。那是一次数据变更，
> 且需要先定义"哪条是权威运行"（`authoritative_run` 的设计意图）。
> 本批只止血，不追溯。

#### 8.9.1 接上了什么

原方案 §7 的落点要求「一次特征/因子计算 + 一份横截面标准化分数 + 5 个策略配置」，

| 组件 | 职责 |
|---|---|

#### 8.9.2 必须说准：省掉的是什么，没省掉的是什么

**省掉了**行情装载与 L1 特征计算。此前 5 个策略各读一次全量行情、各自算一遍
均线/MACD/RSI/波动率，同一只股票在不同策略里可能算出**不同特征**。
现在 5 个策略共享同一份 `FeatureVector`。

**没有省掉** L2 横截面标准化与 L4 排名——**每个策略各做一次**。
这是设计使然：各策略权重不同，加权后的排序必须独立计算。

> 任何声称「5 个策略共享一次标准化结果」的说法都是错的：那样 5 个策略会得到
> **完全相同的排序**，也就没有存在必要。本节的真实数据验证（§8.9.4）恰好证明
> 各策略排序确实不同，这是"独立排名"而非"共享排名"的正面证据。

#### 8.9.3 「只装载一次」是**可执行的断言**，不是注释

`UnifiedFactorMarketLoader` 持有 `AtomicLong loadCount`，记录累计装载次数。
测试 `marketDataIsLoadedExactlyOnceRegardlessOfStrategyCount` 断言：
为 5 个策略产出结果后，该计数只增加 **1**。若将来有人把装载塞回策略循环，测试会失败。

另外 `callingTwiceLoadsTwiceButStillOnlyOncePerCall` 断言两次调用增加 2
（防止"只装载一次"被误实现成"永远只装载一次"的缓存 —— 那会拿到过期数据）。

#### 8.9.4 真实库验证：5 个策略是否真的产出 5 个不同的排序？

**这个问题很关键**：若 5 个策略排序几乎相同，"保留 5 个入口"就失去意义，
而"我们统一了引擎"这类说法最容易掩盖这一点。

只读脚本在真实库（2026-10-13，当日有价股票取前 1200 只）上复刻同一管道，
权重取自 `StrategyCatalog`。

**策略间 finalScore 的 Spearman 秩相关：**

| **趋势打分** | 0.9247 | 1.0000 | 0.8131 | 0.9114 | 0.9328 |
| **超跌反弹** | 0.6957 | 0.8131 | 1.0000 | 0.6877 | 0.7122 |

| **多维度v1** | 0.9986 | 0.9328 | 0.7122 | 0.9982 | 1.0000 |

**Top10 交集：**

- 经典多因子 vs 多维度v1：**10/10**

#### 8.9.5 结论：当前数据环境下，5 个入口实际只有 **3 个不同方法**

**第一，`COMPREHENSIVE` 与 `MULTI_DIM` 在当前数据环境下与 `CLASSIC_SELECTOR` 实质等价。**
最硬的证据不依赖复刻精度：**`CLASSIC_SELECTOR` 的基本面权重为 0**
（其权重表只有技术/动量/量能/风险四类），而它与 `COMPREHENSIVE`（ρ=0.9987）、
`MULTI_DIM`（ρ=0.9986）的排序几乎完全一致、Top10 **逐只相同**。

若这两套方法的基本面维度真的在起作用，它们与"完全不用基本面"的经典多因子的
排序不可能如此一致。这与数据层的实测一致：
`market_data.pe_ratio` / `pb_ratio` **100% NULL**（2,564,591 行）、
`stock_financial_snapshot` **0 行**。基本面因子全部不可用，
其权重被 `RE_NORMALIZE_OVER_AVAILABLE` 就地剔除，于是剩下的排序由同一批技术因子决定，
仅因权重分配略有差异而产生 ρ≈0.999 的微小偏差。

**第二，`TREND` 与 `OVERSOLD_REBOUND` 是真正独立的方法**，与其余各策略
Top10 交集仅 1/10，Top20 独有 15 与 17 只。它们保留了各自的口径差异
（趋势用乖离/MACD/RSI；超跌用反转/量价确认/KDJ）。

**因此当前实际是「3 个不同方法」而不是 5 个**：经典多因子 ≡ 综合三维度 ≡ 多维度v1
（三者同一），加上趋势打分、超跌反弹。

> **这不是统一引擎引入的缺陷**，而是**既有数据层的空洞被统一口径第一次如实暴露出来**。
> 在旧实现里，这三套方法各自用常数填充缺失维度
> （核验报告记录：MULTI_DIM 的 `momentum_score` 恒为 60.0、COMPREHENSIVE 恒为 20.0），
> 表面上看是"5 套独立方法"，实际上其中 3 套的差异来自**不同的常数**而不是不同的信息。
> 统一引擎拒绝用常数充数（d1 决定），于是真实情况显形了。

**这不构成"应该砍掉 2 个入口"的建议。** 恰恰相反：当
`stock_financial_snapshot` 与 PE/PB 被填充后，`COMPREHENSIVE` 与 `MULTI_DIM`
会立刻与经典多因子分离。它们现在是**空转**，不是**冗余**。
判别这两者需要看数据补齐后的行为，而这属于数据层工作（本次范围外）。

#### 8.10.1 接上了什么

`UnifiedScoreReadService` 现在支持 `persist` 参数（**默认 false**）。
开启后它把统一引擎的结果写进**既有** `selector_result` / `selector_result_item` 结构：

| 组件 | 职责 |
|---|---|
| `LegacyResultRowWriter` | 把投影后的条目写成库行，含逐列的缺失语义 |
| `UnifiedScoreReadService.persistStrategy` | 每个策略一条 `selector_result`，带指纹去重 |

**为什么每个策略要一条 `selector_result`**：`strategy_type` 是旧表的分组键，
前端按它取各 tab 的数据。5 个策略合并成一条会让旧读接口直接取不到。
这里是"兼容既有结构"的硬约束在起作用——不是为了少写几行而设计的。

**去重按 `(strategy_type, request_fingerprint, trade_date, SUCCESS)`**，
与 §8.8.5 修掉 41% 重复率的做法同源。命中既有结果时**返回既有 result_id 且不写任何行**，
所以这个方法可以安全地重复调用。

**指纹只纳入影响分数的参数**（`lookbackDays / excludeST / minAvgAmount / minListingDays`），
`topN / persist / dedupe / includeContributions` **刻意不参与**。
理由：把它们纳入的话，一次"只改 topN"的调用会被算成新请求而重复落库——
那正是 41% 重复率的成因模式。这一点由
`fingerprintIgnoresOutputOnlyParametersButTracksScoringInputs` 逐项钉住。

**为什么默认不落库**：写库需要"哪条运行是权威"的语义
（`authoritative_run` / `authority_source` 至今全为 NULL，见 §8.8.6）。
在权威语义确定之前，影子模式必须保持只读。
`persistIsOffByDefaultSoShadowModeStaysReadOnly` 断言默认路径
**一次 `save` 都不调用**。

#### 8.10.2 被测试抓出来的定点缺陷：真实波动率被取整成占位 0

**这是本轮最重要的发现，而且它是我自己刚写下的代码里的缺陷。**

`LegacyResultRowWriter` 第一版直接沿用了既有写入路径的 `round2`（2 位小数）。
测试实测报出：`volatility20` 计算值是 **0.0024171260319901054**，落库后变成 **0.0**。

原因：这些列不是 0-100 量纲的分数，而是**原始行情度量**。
20 日波动率（百分数口径）的典型值在 0.002～0.05 之间，
按 2 位小数取整会把**任何小于 0.005 的波动率压成 0.0**。

**危害与 A-3 完全同类**：0.0 是数据库里"未计算"的占位值，
于是一个**真实算出来的低波动率**与"根本没算"变得不可区分。
而这恰恰是本次重构花了整批 A 去消灭的问题——
如果我没写这个测试，它会以"新代码"的形式把老缺陷原样带回来。

**修法**：新增 `firstDoubleOrNullRaw`（保留完整精度），
只用于 `ret20 / ret60 / volatility20 / max_drawdown60 / avg_amount20` 这 5 列；
0-100 量纲的分数列继续用 `round2`（2 位小数足够，也避免无意义的浮点尾数入库）。

**顺带纠正一个我自己的错误预期**：我最初断言 `max_drawdown60 != 0`，
但**单调上涨序列的 60 日最大回撤本来就只有 0**（没有回撤）。
测试失败暴露的是我的预期错了，不是代码错了。这条被改成注释保留在测试里：
它恰好证明**"用 0 判断是否未计算"本身不可靠**，必须靠 NULL 区分——这正是 A-3 的立论依据。

两个方向的要求现在同时被断言：
- `realZeroIsPreservedAsZeroRatherThanBecomingNull`：真实 0 必须保持 0；
- `missingNullableColumnsBecomeNullAndMissingScoreColumnsBecomeZero`：
  缺失必须变 NULL，而 NOT NULL 列缺失才落 0。

#### 8.12.1 V30 迁移的回填在真实执行时自我失效（已用 V31 修复）

**现象**：V30 应用后，四列的实测值与 V30 文件自述的验收标准直接矛盾：

| 列 | V30 自述期望（=0 / IS NULL） | V30 执行后实测 | 判定 |
|---|---|---|---|
| ret20 | 4 / 2733 | **4 / 2733** | ✅ 符合 |
| ret60 | 0 / 2733 | **2733 / 0** | ❌ 完全失配 |
| volatility20 | 0 / 2733 | **2733 / 0** | ❌ 完全失配 |
| max_drawdown60 | 0 / 2853 | **2733 / 120** | ❌ 只命中 120 行 |

V30 文件第 62 行还要求 `ret20 IS NULL AND ret60 IS NOT NULL` 恒为 0，实测为 **2733**。

**根因（已用只读查询逐条证实）**：V30 用 4 条独立 UPDATE 回填，但每条都重新测试
`ret20 = 0`。第 1 条先把 ret20 置为 NULL，而 SQL 中 **`NULL = 0` 的结果是 NULL 而非 TRUE**，
于是第 2~4 条的 WHERE 从那一刻起永远不可能为真。

证实方式：
- 当前 `ret60=0 AND ret20=0 AND vol20=0 AND mdd60=0` → **0 行**（迁移时本应 2733）；
- 把谓词放宽为 `(ret20 = 0 OR ret20 IS NULL)` → **2733 行**；
  ⟹ 失配确由 ret20 已变 NULL 造成，而非行集变化。
- 第 4 条之所以命中 120 行，恰是它含 `OR (ret20 <> 0 OR ret60 <> 0 OR volatility20 <> 0)`

#### 8.12.2 `persist=true` 真实写入失败：事务被标为只读（已修复）

**现象**：`POST /engine/all-strategies` 带 `persist=true` → **HTTP 500**（`ERR-500-A28C5C5C`）。
后端日志给出确切原因：

```
SQL Error: 0, SQLState: S1009
Connection is read-only. Queries leading to data modification are not allowed
    at UnifiedScoreReadService.persistStrategy(UnifiedScoreReadService.java:267)
```

**根因**：`runAllStrategies` 被标注 `@Transactional(readOnly = true)`，
但它后来被加上了落库能力。Hikari 按只读打开连接，任何 INSERT 都被拒绝。

**为什么所有测试都没抓到**：单元测试用 mock 的 repository，从不真正执行 SQL，
因此"连接是否只读"这一层完全没有被覆盖。

**修法**：方法改为 `@Transactional`（可写）。只读声明保留在
`UnifiedFactorMarketLoader.load`（它只读且确实只读）。
并新增回归测试 `runAllStrategiesIsNotReadOnlyTransactionalBecausePersistWrites`，
用反射读取 `@Transactional` 注解并断言 `readOnly()` 为 false——
把这个曾经静默的失误变成可执行契约。

**修后实测**：`persist=true` → **HTTP 200**，新增 5 条 `selector_result`
（五个旧口径 `strategy_type` 各一条，`factor_version=unified_factor_all_strategies_v1`）

#### 8.12.5 重要更正：§8.9.4 的结论受复刻简化影响

真实引擎的 Top10 交集与 §8.9.4 的 Python 复刻**明显不同**：

| 对比 | §8.9.4（复刻） | **真实引擎（本轮实测）** |

**原因**：Python 复刻没有实现 L2 的 `LOG_MV_ONLY_REGRESSION` 市值中性化，
而真实引擎走了完整的 winsorize → 中性化 → 稳健Z → 百分位管道。
市值中性化显著改变了各策略头部的重叠结构。

**因此 §8.9.5 的结论需要收窄**。仍然成立的部分是**静态事实**：
`CLASSIC_SELECTOR` 的基本面权重为 0，而 `COMPREHENSIVE`/`MULTI_DIM` 有 40% 权重
压在 PE/PB/财务快照上——这些数据在当前库中填充率为 0，所以那 40% 是空转。
这一点由 §8.12.4 的 `non_fundamental_weight_share=0.6` 独立佐证。

**但"因此这三个入口的排序几乎相同"不成立**：真实引擎下 CLASSIC 与 COMPREHENSIVE
的 Top10 **零重叠**。差异来自权重分配与市值中性化的交互，而非基本面信息。

**正确表述**：基本面维度当前**不贡献任何信息**（数据为空）；
`COMPREHENSIVE`/`MULTI_DIM` 与 `CLASSIC_SELECTOR` 的差异**全部来自技术因子权重的重新分配**。
这仍是"空转而非冗余"，但**不能**再声称它们的排序等价。

> 这也再次印证本方案的一贯立场：复刻/近似结论只能作为**假设**，
> 必须由真实引擎实测取代。§8.9.4 的排序结论属于已被本轮实测取代的部分。
