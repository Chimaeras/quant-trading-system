# Codex 量化系统持续优化执行协议

## 1. 用途

本文件用于指导 Codex 对 `quant-trading-system` 进行长期、循环、可验证的持续优化。

本协议只允许操作以下仓库：

```text
本地目录：E:\Project\quant-trading-system
GitHub：https://github.com/Chimaeras/quant-trading-system.git
远程：origin
默认分支：master
```

用户口头所称的 `quant_trading` 项目，在本协议中统一指向上述
`quant-trading-system` 仓库，不得误操作 `E:\Project` 下的其他项目。

Codex 不需要照搬 Cursor 的 `/loop` 命令。推荐使用以下组合实现同等效果：

```text
Codex长期目标（Goal）
  + 本执行协议
  + 持久化进度文件
  + 每轮验证
  + 自动续跑
  + 明确停止条件
```

如果希望每天或每隔固定时间执行一轮，则使用 Codex Automation。

## 3. 长期目标

将当前项目逐步建设成一套可信赖的个人量化研究与交易决策辅助系统，优先形成：

```text
可信行情与财务数据
→ 历史时点股票池
→ 可解释因子
→ 严格回测
→ 样本外验证
→ 每日买入/持有/卖出/无机会信号
→ 目标仓位与风险提示
→ 人工执行和实际绩效记录
→ QMT只读对账
→ 受控自动交易
```

当前优先级（P0 之后的主航道见 `docs/选股迭代优先方向.md`）：

```text
金融正确性与数据时点
→ 选股因子与多策略打分能力
→ 股票池与可交易性过滤
→ 选股可解释性与筛选体验
→ 打分回测（验证选股效果）
→ 单股策略回测 / 模拟交易
→ 风险管理
→ 测试与工程质量
→ 自动交易
```

不得优先建设与当前阶段无关的微服务、复杂机器学习、高频交易或华丽页面。

## 4. Codex循环模型

一次长期目标由多个“目标回合”组成，每个回合完成一轮闭环。

```text
读取进度
→ 扫描一个主题
→ 发现候选问题
→ 选择最高优先级问题
→ 建立修改前证据
→ 实施最小完整修复
→ 增加回归测试
→ 编译与运行验证
→ 更新进度文件
→ 判断停止条件
→ 未满足则进入下一目标回合
```

每个回合只处理：

- 一个独立问题；或
- 一组不可分割的强相关问题。

不得在一个回合内同时重构多个无关模块。

## 5. 每轮执行步骤

### 第一步：读取状态

必须检查：

- 执行协议；
- 优化手册；
- 进度文件；
- Git状态；
- 用户已有修改；
- 上一轮测试结果；
- 上一轮残余风险。

### 第二步：选择扫描主题

每轮只选择一个（**默认从选股相关主题开始轮换**，见 `docs/选股迭代优先方向.md`）：

1. 未来函数与金融正确性；
2. 行情数据质量（选股输入）；
3. 选股因子、评分口径与质量闸；
4. 股票池与可交易性；
5. 选股结果可解释性与前端筛选体验；
6. 打分回测与选股效果验证；
7. 单股策略回测成交模型；
8. 组合与仓位管理；
9. 风险控制；
10. 测试覆盖；
11. 前后端契约；
12. 数据库与并发；
13. 性能；
14. 安全；
15. 日志、监控与部署；
16. 文档一致性。

### 第三步：提供证据

修改前必须明确：

- 问题位置；
- 复现方式；
- 当前错误行为；
- 对金融结果或系统稳定性的影响；
- 优先级；
- 修改风险；
- 验证方法。

没有证据的问题不进入修改阶段。

### 第四步：实施修改

要求：

- 保留用户无关修改；
- 不进行破坏性Git操作；
- 不修改任务范围外的代码；
- 不用Mock或异常吞噬掩盖错误；
- 数据库变更考虑旧数据兼容；
- 金融计算写明口径和时点；
- API变更同步前端类型和文档。

### 第五步：验证

最低验证：

```powershell
mvn test '-Dskip.frontend.build=true'

cd modules/web
npm exec vue-tsc -- --noEmit
npm run build
```

涉及Python时：

```powershell
python -m pytest
```

涉及API或页面时：

```text
启动应用
→ 验证目标API
→ 验证目标页面
→ 检查后端日志
→ 检查浏览器错误
```

测试失败时必须继续修复，不得通过删除测试、降低断言或跳过检查宣布成功。

### 第六步：记录与提交

每轮必须更新：

```text
.cursor/optimization-progress.md
```

记录内容：

- 当前轮次；
- 扫描主题；
- 发现的问题；
- 修改文件；
- 新增测试；
- 验证结果；
- 未解决风险；
- 下一轮建议；
- 连续无新增P0/P1/P2轮数；
- `上次提交轮次`、`批次内待提交轮数`（与 Cursor 手册一致）。

**提交策略（与 Cursor 手册对齐）**：

- **批次内（第 1–9、11–19… 轮）**：验证通过后**仅更新进度文件**，不 `git commit`。
- **第 10、20 轮**或用户要求停止/提交时：`git add -A` → 一条批次 commit（概括该 10 轮）→ `git push origin HEAD` → `git status` 干净。
- **批次起始轮**（1/11/21…）：开始前工作区须干净。

批次提交示例：

```powershell
git add -A
git commit -m "fix(优化批次X-Y): <摘要>"
git push origin HEAD
git status
```

要求：

1. `git add -A` 必须覆盖仓库内全部变动。
2. commit message 应描述批次内实际修复，尤其是选股/打分相关改动。
3. 推送目标：`origin HEAD`（默认 `master`）。
4. push 成功后工作区干净。
5. 不创建 PR、不发布版本、不操作其他仓库。
6. 测试未通过时不得提交。
7. push 失败时停止并报告用户；批次边界不得在未 push 时开始下一批次。

### 第七步：等待下一轮

与 Cursor 一致时：**30 秒**（`/loop 30s`）；若使用 Codex Automation 可自行设为 5 分钟，但须遵守相同批次提交规则。

等待期间不得继续修改文件。下一轮开始前检查 `git status`；批次起始轮须干净。

### 第八步：继续或停止

未满足停止条件时，不得因为完成一个局部修复就结束长期目标。

## 6. 停止条件

满足以下全部条件，Codex才可以将长期目标标记为完成：

1. 连续两轮完整扫描没有发现新的P0、P1或P2问题；
2. 进度文件不存在未处理P0或P1；
3. 后端测试全部通过；
4. 前端类型检查通过；
5. 前端生产构建通过；
6. Python测试通过，如果Python模块仍被使用；
7. 核心API冒烟通过；
8. 核心页面冒烟通过；
9. 剩余问题只有P3、主观风格或需要用户决策的事项；
10. 已输出最终审查报告。

满足以下任一条件时暂停并请求用户，而不是擅自决定：

- 需要证券账户、密码、Token或API Key；
- 需要决定交易对象、策略方向、风险偏好或资金规模；
- 需要删除大量数据；
- 需要不可逆数据库迁移；
- 需要启用真实自动交易；
- 不同方案会显著改变产品方向；
- 外部服务或测试环境持续不可用；
- 同一阻塞条件连续出现三轮；
- 达到20轮。

“工作时间较长”“上下文较长”或“已经修了很多问题”不是停止理由。

## 8. 在Codex中启动长期目标

推荐在项目线程中发送：

```text
请为当前项目创建一个长期目标：

持续优化 quant-trading-system，
严格按照
@docs/选股迭代优先方向.md
@docs/Codex量化系统持续优化执行协议.md
@docs/Cursor量化系统持续优化执行手册.md
执行。

业务主航道：优先选股与多策略打分能力（因子、质量闸、股票池、可解释性、筛选体验）。

每个目标回合只完成一轮「扫描—证据—修复—测试—记录」闭环。
每轮更新 .cursor/optimization-progress.md。
批次内（非 10 倍数轮）不 commit；第 10/20 轮 git add -A 批次提交并 push。
未满足停止条件时持续进入下一回合。循环间隔建议 30s。最多 20 轮。

不要创建 PR、发布版本、启用真实交易或操作其他项目。
```

如果只想试运行一轮：

```text
按照 @docs/Codex量化系统持续优化执行协议.md
执行一轮优化，不创建长期目标。
完成后更新进度文件并停止。
```

## 9. 使用Codex Automation分批迭代

如果不希望一个线程连续运行，可以创建定时自动化，让Codex每天执行一轮。

推荐自动化要求：

```text
名称：量化系统每5分钟优化一轮
工作目录：E:\Project\quant-trading-system
频率：每5分钟
运行环境：本地工作区
每次范围：只完成一轮
```

自动化提示词：

```text
阅读：
1. docs/选股迭代优先方向.md
2. docs/Codex量化系统持续优化执行协议.md
3. docs/Cursor量化系统持续优化执行手册.md
4. .cursor/optimization-progress.md

仅执行一轮；**优先选股/打分主航道**上的最高优先级问题：

扫描一个主题（默认选股相关）
→ 提供问题证据
→ 修复一个最高优先级问题
→ 增加回归测试
→ 完成全部相关验证
→ 更新 .cursor/optimization-progress.md
→ 仅当第 10/20 轮或用户要求时：git add -A 批次提交并 push
→ 输出本轮报告。

不要创建PR、发布版本、启用真实交易或操作其他仓库。
测试失败、push失败、发生冲突或工作区含无关脏改时，停止并报告用户。
```

自动化每5分钟执行一轮。由于每轮都要直接推送 `origin master`，必须串行执行，
不得让多个自动化实例并发修改同一工作区。

## 10. 建议的执行策略

### 方案A：长期目标

适合：

- 希望Codex持续工作；
- 各轮之间需要紧密上下文；
- 允许在当前工作区连续修改；
- 希望达成停止条件后自动结束。

### 方案B：每日自动化

适合：

- 每天只处理一个问题；
- 希望每轮独立审查；
- 希望使用worktree隔离；
- 不急于一次完成。

### 方案C：先目标后自动化

推荐实践：

1. 先用长期目标集中处理P0/P1；
2. 人工审核；
3. 再用每日自动化处理新增问题和维护性工作。

## 11. 人工检查点

每3至5轮暂停一次，向用户汇报：

- 已完成问题；
- 当前测试情况；
- 金融可信度变化；
- 代码规模变化；
- 是否出现架构漂移；
- 是否需要业务决策；
- 下一阶段建议。

长期自治不代表可以省略人工审计，尤其是金融策略、风险参数和实盘接口。
