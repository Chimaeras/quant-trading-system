## 1. ⭐ 那个伪造"强正 alpha"的 bug

### 1.1 错误代码

```python
codes = sorted(bycode)          # ← bycode 是 dict[code -> 因子值]；sorted() 排的是【键】
n = len(codes)
pct = {}
for rank, c in enumerate(codes, 1):
    pct[c] = rank / n * 100.0   # ← 赋的是"代码在代码表里的位次"
```

正确写法（**必须按键对应的值排序**）：

```python
codes = sorted(bycode, key=lambda c: bycode[c])
```

### 1.2 症状：两个不同因子输出逐位相同

| 检验 | 结果 |
|---|---|
| `EP` 与 `BP` 原始值是否相同 | **不同**（`pearson(EP,BP) = 0.1981`） |
| 排序位次相同的股票数 | **1 / 5,360** |
| 但我算出的**百分位**相同的股票数 | **5,360 / 5,360（全部）** |
| 二者 IC | **0.047531 = 0.047531**（同一个数） |

> **`EP` 与 `BP` 是两个不同的量（相关性仅 0.20、排序几乎无重合），
> Spearman 秩相关不可能相同。**"输出完全相同"本身就是一个不可能事件，
> 这是唯一暴露 bug 的线索。

### 1.3 伪造出的结论 vs 修正后的结论

| | 全窗口 k=20 日均净 | t | 解读 |
|---|---|---|---|
| **有 bug 版** | **+0.3066%** | **+5.38** | "估值因子有强正 alpha，满足 t>2 且净>0，**保留**" |
| **修正版** | **−0.1561%** | **−2.45** | **符号翻转，不保留** |

**若我没有核对"两个因子是否应该不同"，这个假结论会被写进文档并作为"目标(5) 达成"上报。**

## 2. 回填进程僵死：诊断与修复

### 2.1 症状

| 观测 | 值 |
|---|---|
| 日志停在 | `[190/219]`，超过 40 分钟无新增 |
| PID 51576 CPU | 6 秒内 **delta 0.0s** |
| 工作集 | 仅 **16~17 MB** |
| 对应 MySQL 连接 `id=1239` | `Sleep` **1783 秒** |
| MySQL 活跃查询（`command<>'Sleep'`） | **无** |
| 但**后端 `/engine/all-strategies` 实测正常** | 2026-08-19 用 **133.5s** 成功落库 |

> ⟹ **引擎健康、DB 健康，是回填脚本的 socket 僵死。**
> （先做这一步排除很重要 —— 否则会误判为"引擎挂了"而去重启后端。）

### 2.2 根因

`backfill_cross_section.py:85` 原为 `urlopen(req, timeout=7200)` —— **2 小时**。
引擎实测 45~140s，2 小时超时意味着：**一旦 socket 僵死，进程会静默挂满 2 小时且几乎不耗 CPU。**

### 2.3 修复

```python
# 引擎实测 45~140s。原为 7200s(2h) —— 一旦 socket 僵死会静默挂 2 小时
with urllib.request.urlopen(req, timeout=600) as r:
```

- 终止僵死进程 → **DB 进度完好**（377 截面日 / 6,944,815 行；`backfill_state.json` 249 项）
- 从 2026-08-20 重启，剩 29 日，ETA ~62 分钟
- 结论：**续跑机制有效，僵死未损坏数据**

## 5. 方法轮教训（新增）

70. ⭐⭐ **截面百分位必须按「因子取值」排序，绝不能按「标的代码」排序** ——
    我写成 `sorted(bycode)` 再赋 `rank/n`，得到的是"代码的百分位"，
    **与因子取值无关**。后果是 `VAL_EP` 与 `VAL_BP` 百分位逐位相同，
    并**伪造出 +0.3066%/日、t=+5.38 的"强正 alpha"**（真值 −0.1561%、t=−2.45）。
    **诊断口诀：任何"按值排序"的统计，都要先确认排序键是值本身。**
71. ⭐⭐ **"两个本应不同的量给出完全相同的结果"是不可能事件，必须立即停手排查** ——
    `EP`/`BP` 相关性仅 0.20、排序几乎无重合，Spearman 却输出同一个数（0.047531）。
    **这个"不可能"是唯一暴露 bug 的线索**，其价值高于那个假结论。
    **它也是把假结论挡在文档之外的最后一道防线。**
72. **发现"漂亮结果"时必须主动去找使它不成立的理由** ——
    本轮若只看到 `+0.31%/日、t=+5.38`（恰好满足目标"t>2 且净>0"的保留门槛）
    就会直接宣布目标达成。**"刚好满足判据"的结果应触发加倍怀疑，而不是庆祝。**
73. **进程僵死与引擎故障必须分开诊断** —— 回填日志停住时，
    我先测了后端 `/engine/all-strategies`（133.5s 正常）与 MySQL 活跃查询（无），
    才定位到是**脚本 socket 僵死**，而非引擎问题。
    **否则会错误重启健康的后端，并掩盖真正原因。**
74. **网络超时必须与实测耗时长度量级匹配** —— 引擎实测 45~140s，
    却设了 `timeout=7200`（2 小时，约 50 倍）。**过长超时把"快速失败"变成"静默挂死"。**
75. **运行时手工建表必须补版本化迁移** —— 第 9 轮直接 `CREATE TABLE`，
    但本项目 Flyway 是唯一真相源且 `ddl-auto: validate`；
    不补 `V34` 则**新建库缺表**。**"能跑"不等于"可复现"。**
