# Cursor 量化系统持续优化执行手册

## 1. 文档用途

本文件是 Cursor Agent 对 `quant-trading-system` 执行长期、循环式优化时的最高层任务说明。

**业务主航道**见 `docs/选股迭代优先方向.md`（选股能力、数据分析准确性、可解释筛选结果优先于无关工程美化）。

目标不是无边界地“美化代码”，而是站在以下两个视角持续完善系统：

1. 计算机工程视角：正确性、架构、测试、安全、性能、可观测性、部署和可维护性。
2. 金融量化视角：数据时点、策略有效性、回测可信度、交易可实现性、风险控制和合规性。

Cursor 每轮只处理一个经过证据确认的最高优先级问题，完成修改和验证后重新扫描，直到满足停止条件。

---

## 2. 最终建设目标

将当前项目逐步建设成一套面向个人投资者的、可信赖的量化研究与交易决策辅助系统，形成以下闭环：

```text
可信数据
  → 股票池管理
  → 因子与策略研究
  → 严格回测
  → 样本外验证
  → 每日选股与买卖信号
  → 人工确认执行
  → 实际成交记录
  → 绩效归因
  → 风险监控
  → 后续接入 QMT 自动交易
```

当前阶段优先建设：

```text
行情数据 → 选股评分（多策略）→ 可解释候选列表 → 买卖信号 → 回测验证 → 人工执行建议
```

**持续优化时**：在 P0 清零后，默认优先改进 **选股与打分链路**（因子口径、质量闸、股票池、可交易性、选股页与结果解释），详见 `docs/选股迭代优先方向.md`。

自动交易、复杂微服务、机器学习预测和高频交易不属于当前最高优先级。

## 3. 基本工作原则

### 3.1 必须遵守

1. 修改前先阅读本文件、`README.md`、相关业务文档以及当前 Git diff。
2. **批次起始轮**（第 1、11、21… 轮，或上一批次刚 push 完成后）须确认 `git status` 工作区干净；**批次内**（第 2–9、12–19… 轮）允许保留本循环产生的未提交改动，但必须先 `git diff` 确认无无关修改。
3. 每轮只处理一个问题或一组强相关问题。
4. 必须先证明问题存在，再修改代码。
5. 修改范围必须与问题直接相关。
6. 修改后必须执行与风险相匹配的验证。
7. 不允许通过降低测试标准、吞掉异常或返回假数据使验证“通过”。
8. 不覆盖用户已有的无关修改。
9. 不执行 `git reset --hard`、强制覆盖或其他破坏性命令。
10. **每 10 轮**（第 10、20 轮，或提前停止/用户要求提交时）将 **quant-trading-system 项目下全部变动**（`git add -A`）**批次提交**并推送到 GitHub；commit message 须概括该批次内各轮修复与验证结果；push 后再次确认工作区干净；不创建 PR 或发布。**批次内第 1–9 轮验证通过后仅更新进度文件，不得单独 commit。**
11. 数据库变更必须考虑旧数据和升级兼容性。
12. 前后端字段变化必须同步修改类型、页面和接口文档。
13. 所有金融指标必须写明计算口径、数据时点和适用范围。

### 3.2 禁止行为

- 为了继续循环而制造没有业务价值的修改。
- 仅基于个人偏好进行全项目格式化。
- 在没有测试或数据证据时调整因子权重。
- 使用当前股票池回测历史时期而不说明幸存者偏差。
- 使用未来才公布的数据计算历史信号。
- 使用信号日收盘后才能得到的信号，却假设按该收盘价成交。
- 将技术指标推断结果命名成真实新闻、机构评级或资金流数据。
- 在正式模式静默生成随机行情或随机选股结果。
- 把接口调用成功等同于交易已成交。
- 一次性实施大规模架构重写。

## 4. 优先级定义

每个问题必须先分级。

### P0：必须立即处理

- 未来函数、数据泄漏或严重回测失真。
- 可能生成明显错误买卖信号。
- 数据写错、重复、串股票或串日期。
- 可能造成重复下单、超额交易或资金风险。
- 密钥、账户密码等敏感信息泄漏。
- 数据库破坏、不可恢复或严重并发错误。
- 核心功能无法启动、无法编译或无法运行。

### P1：高优先级

- 缺少核心测试。
- 股票池存在明显幸存者偏差。
- 未处理停牌、涨跌停、ST、新股或退市状态。
- 回测未考虑费用、滑点和成交约束。
- 打分阈值被绕过，强行输出不合格候选。
- 数据质量没有校验。
- 前后端契约不一致。
- 任务重试可能产生重复结果。
- 核心计算性能无法覆盖目标股票池。
- 重要业务含义与字段命名不一致。

### P2：中优先级

- 可维护性差、重复实现或模块职责混乱。
- 错误处理、日志和监控不足。
- 构建、配置或部署不稳定。
- 页面容易误导用户。
- 文档和实现不一致。
- 查询和批量计算存在明显性能问题。

### P3：低优先级

- 局部命名、注释、样式和非关键交互体验。
- 对当前规模没有实际收益的架构升级。
- 主观性的代码风格调整。

工作顺序必须为：

```text
P0 → P1 → P2 → P3
```

在 **P0/P1 金融正确性** 与 **选股主航道**（见 `docs/选股迭代优先方向.md`）之间：未来函数、错误信号、数据时点错误始终最优先；其后优先选股因子、股票池与可交易性，再处理回测/下单与纯工程项。

存在P0或P1时，不处理纯样式问题。

## 5. 量化金融审查框架

### 5.1 数据层

逐项检查：

- 行情来源是否明确、稳定、可追溯。
- OHLC、成交量、成交额和复权口径是否一致。
- 前复权、后复权和不复权分别用于什么场景。
- 是否保存原始数据和数据源标识。
- 是否校验重复日期、缺失日期、非法价格和异常成交量。
- 是否使用真实交易日历，而不是简单排除周末。
- 股票代码和交易所映射是否正确。
- 是否记录上市、退市、ST、停牌和涨跌停状态。
- 是否支持历史时点股票池。
- 财务数据是否记录报告期和公告日期。
- 历史计算是否只使用信号日前已经公开的数据。
- 数据更新失败后是否可重试且不会重复写入。
- 多数据源冲突时是否有确定且可审计的优先级。
- 实时行情过期时是否会阻止产生交易信号。

### 5.2 股票池

系统应逐步支持：

- 市场范围配置：沪市、深市、创业板、科创板、北交所。
- 指数历史成分股。
- 上市时间过滤。
- ST、退市整理、停牌过滤。
- 流动性过滤。
- 最小成交额和换手率过滤。
- 涨跌停及不可交易状态过滤。
- 行业集中度限制。
- 用户自选股票池和ETF池。
- 每次运行保存股票池快照。

任何历史回测都必须能够回答：

> 在当时那个交易日，系统实际知道并允许交易哪些股票？

### 5.3 因子与指标

每个因子必须包含：

- 唯一名称和版本。
- 数学定义。
- 输入字段。
- 所需历史窗口。
- 缺失值处理。
- 极值处理。
- 标准化方式。
- 因子方向。
- 数据可用时间。
- 适用证券范围。
- 单元测试。

建议逐步增加：

- 因子覆盖率。
- 截面分布。
- Rank IC、IC均值和ICIR。
- 分组收益。
- 多空收益，仅用于研究评价。
- 因子换手率。
- 因子相关性和共线性。
- 不同市场阶段的稳定性。

禁止只因为历史收益好看就提高某个因子权重。

### 5.4 策略与信号

策略必须明确区分：

```text
候选股票
≠ 买入信号
≠ 目标持仓
≠ 实际订单
≠ 实际成交
```

每个信号至少应包含：

- 证券代码和名称。
- 信号日期。
- 信号类型：买入、持有、减仓、卖出、观察。
- 综合得分和排名。
- 触发原因。
- 失效条件。
- 建议仓位。
- 参考执行时间。
- 风险提示。
- 策略版本和参数快照。

系统必须允许：

```text
当天没有符合条件的标的。
```

不得为了填满TopN而输出不符合质量阈值的股票。

### 5.5 回测

回测必须逐步具备：

- 信号生成时间和可成交时间分离。
- 次日开盘、VWAP或其他明确成交模型。
- 买卖佣金。
- 印花税等卖出费用。
- 滑点。
- 最低佣金和最小交易单位。
- 停牌处理。
- 涨跌停无法成交处理。
- T+1处理。
- 成交量和市场冲击限制。
- 重叠持仓处理。
- 现金和仓位管理。
- 定期调仓。
- 组合净值。
- 基准净值。
- 最大回撤。
- 年化收益。
- 波动率。
- 夏普比率和Calmar比率。
- 换手率。
- 胜率、盈亏比和连续亏损。
- 年度与月度收益。
- 牛市、熊市和震荡市分段表现。

回测报告必须显示成交与费用假设，不允许隐藏。

### 5.6 策略验证

必须按照以下顺序验证：

1. 单元测试和固定样例。
2. 历史开发区间。
3. 验证区间。
4. 完全隔离的样本外区间。
5. Walk-forward滚动验证。
6. 参数敏感性分析。
7. 实时影子运行。
8. 人工确认的小资金实盘。

重点识别：

- 未来函数。
- 幸存者偏差。
- 过拟合。
- 数据挖掘偏差。
- 参数对单一年份过度依赖。
- 交易成本后收益消失。
- 少量极端股票贡献全部收益。

### 5.7 风险管理

系统应逐步支持：

- 单只证券最大仓位。
- 行业最大仓位。
- 总仓位上限。
- 现金比例。
- 单笔最大金额。
- 单日最大交易额。
- 单日最大亏损。
- 组合最大回撤保护。
- 波动率目标仓位。
- 信号过期保护。
- 行情过期保护。
- 重复信号保护。
- 黑名单。
- 人工暂停开仓。
- 紧急停止。

即使暂时人工交易，系统也应输出目标仓位和风险检查结果。

### 5.8 QMT与实盘接口

当前不是最高优先级，但架构需要预留：

- 独立的券商适配层。
- 行情接口与交易接口解耦。
- 查询资金、持仓、委托和成交。
- 下单、撤单和回报回调。
- 断线检测与主动重连。
- 本地订单号和券商订单号映射。
- 部分成交、废单和撤单状态。
- 幂等下单和重复订单保护。
- 启动时券商状态对账。
- 券商账户作为持仓最终事实来源。
- 模拟账户、只读模式和人工确认模式。
- 程序化交易报备及频率限制。

在订单管理和风控完善前，不启用无人值守实盘下单。

## 6. 软件工程审查框架

### 6.1 架构

检查：

- 前端、后端、Python模块和数据库的职责是否清晰。
- 是否存在Java与Python重复实现同一指标但口径不同。
- Controller是否包含过多业务逻辑。
- Service是否职责过大。
- 数据源是否通过接口抽象。
- 策略是否直接依赖具体行情或券商实现。
- DTO、实体和页面模型是否被不恰当地混用。
- 是否为了当前规模引入不必要的微服务复杂度。

默认优先模块化单体，不主动拆微服务。

### 6.2 正确性

重点检查：

- 日期边界。
- 交易日偏移。
- 空值和零值。
- 浮点精度。
- 百分数和小数混用。
- 股票代码与交易所组合键。
- 并发任务重复执行。
- 事务边界。
- 任务取消和恢复。
- 排序稳定性。
- 分页和总数。
- 前后端字段命名。

### 6.3 测试

逐步建立：

- 技术指标单元测试。
- 因子评分边界测试。
- 数据解析测试。
- 数据时点测试。
- 回测成交模型测试。
- 费用计算测试。
- 股票池过滤测试。
- Repository集成测试。
- API契约测试。
- 前端关键计算测试。
- 端到端冒烟测试。

修复Bug时必须先添加能复现问题的测试，或在同一轮补充回归测试。

### 6.4 性能

检查：

- N+1数据库查询。
- 全表加载。
- 无边界时间范围。
- 大对象响应。
- 缺少索引。
- 重复计算技术指标。
- 不受控线程池。
- 批量任务内存占用。
- 前端过大Bundle。
- 不必要的同步阻塞。

性能优化前应记录基线；没有测量证据时，不做复杂优化。

### 6.5 安全

检查：

- 密码和密钥是否硬编码。
- 日志是否输出敏感信息。
- SQL注入。
- 任意文件访问。
- 未限制的批量接口。
- CORS和认证。
- 调试接口暴露。
- 第三方依赖风险。
- 外部HTTP数据可信边界。

个人本地系统也不能把券商密码、Token或API Key写入仓库。

### 6.6 可观测性

逐步支持：

- 结构化日志。
- 请求和任务ID。
- 数据更新时间。
- 数据源。
- 策略版本。
- 参数快照。
- 耗时和处理数量。
- 成功、失败和跳过原因。
- 健康检查。
- 关键异常告警。

### 6.7 构建与部署

要求：

- Java、Node、Python版本明确。
- 一条命令可执行测试。
- 一条命令可构建。
- 配置通过环境变量覆盖。
- 构建过程可重复。
- 应用启动时不隐式执行依赖安装。
- 数据库迁移可版本化。
- Docker配置与本地配置一致。
- README与实际启动方式一致。

### 6.8 前端

检查：

- TypeScript检查通过。
- 页面不静默展示Mock数据。
- 空状态、加载状态和错误状态明确。
- 所有收益和百分比单位一致。
- 用户能看到策略版本、数据日期和计算假设。
- “推荐”“情绪”“机构评级”等字段不会夸大数据能力。
- 高风险操作有明确确认。
- 表格和图表展示同一口径。

## 7. 每轮循环执行流程

每轮严格执行以下步骤。

### 步骤1：恢复上下文

阅读：

- 本文件。
- `.cursor/optimization-progress.md`。
- 当前 Git 状态和 Git diff。
- 与候选问题相关的代码和文档。

**前置条件**：

- **批次起始轮**（第 1、11、21… 轮）：`git status` 须干净（无 staged/unstaged/untracked 待提交项）。
- **批次内**（第 2–9、12–19… 轮）：允许存在本循环产生的未提交改动；开始前执行 `git status` 与 `git diff`，若含与当前优化任务无关的改动，停止并报告用户，不得覆盖。
- **批次边界**（第 10、20 轮完成验证后）：执行步骤 7b 批次提交并 push，再进入下一轮。

如果进度文件不存在，按本文件第9节创建。

### 步骤2：扫描

本轮只选择一个扫描主题：

1. 金融正确性。
2. 数据质量与数据时点。
3. 股票池与可交易性。
4. 因子与策略。
5. 回测可信度。
6. 风险管理。
7. 测试覆盖。
8. 前后端契约。
9. 性能。
10. 安全。
11. 构建部署。
12. 文档一致性。

扫描后列出最多5个候选问题，并提供：

- 文件和代码位置。
- 复现方式。
- 影响。
- 优先级。
- 修复成本。

### 步骤3：选择

选择一个最高优先级且本轮可以完整验证的问题。

选择标准：

```text
真实影响 × 发生概率 × 可验证性 ÷ 修改风险
```

### 步骤4：建立基线

修改前记录：

- 当前行为。
- 当前测试结果。
- 当前性能数据，若涉及性能。
- 当前API返回，若涉及接口。

### 步骤5：修改

- 只修改必要文件。
- 尽量保持向后兼容。
- 新增配置必须有安全默认值。
- 新增金融计算必须说明口径。
- 数据库字段必须考虑旧数据。
- 不顺手重构无关代码。

### 步骤6：验证

最低验证命令：

```powershell
mvn test '-Dskip.frontend.build=true'
cd modules/web
npm exec vue-tsc -- --noEmit
npm run build
```

如果改动涉及Python：

```powershell
python -m pytest
```

如果改动涉及页面或API：

- 启动应用。
- 验证对应API。
- 验证对应页面。
- 检查后端日志和浏览器控制台。

### 步骤7：记录

更新 `.cursor/optimization-progress.md`：

- 问题。
- 证据。
- 修改文件。
- 验证结果。
- 残余风险。
- 下一轮建议。

### 步骤7b：批次提交与推送

**触发时机**（满足任一即执行）：

- 当前轮次为 **10 的倍数**（第 10、20 轮）且本批次验证已全部通过；
- 达到停止条件或用户要求停止，但工作区仍有本循环未提交变动；
- 用户明确要求立即提交。

**批次内第 1–9 轮**：完成步骤 7 后即可进入步骤 8，**跳过**本步骤。

执行步骤：

1. `git add -A` 暂存 **项目下全部变动**（含文档、前后端、配置等）。
2. 编写 commit message，格式建议：`fix(优化批次X-Y): <摘要>`，正文按轮次列出各轮优先级、根因、主要修改与验证结果。
3. `git commit` 后 `git push origin HEAD`。
4. 执行 `git status`，确认工作区 **完全干净**；若不干净，继续提交直至干净。
5. 在进度文件的「已完成问题」表中为本批次各轮记录 **同一** commit hash（短 SHA），并更新「上次提交轮次」。

若 push 失败（权限、冲突、网络），停止循环并报告用户；**批次边界**不得在未 push 的情况下开始下一批次。

### 步骤8：重新扫描

完成后等待 **30 秒** 再开始下一轮，不得因为一个问题修复成功就宣布整个长期任务完成。

## 8. 停止条件

满足以下全部条件才允许正常停止：

1. 连续两轮完整扫描未发现新的P0、P1或P2问题。
2. 后端测试全部通过。
3. 前端类型检查通过。
4. 前端生产构建通过。
5. Python测试通过，若Python模块仍在使用。
6. 核心页面和API冒烟验证通过。
7. 进度文件中没有未处理的P0或P1。
8. 剩余项目只有P3、主观风格或需要用户业务决策的事项。

此外，满足以下任一条件必须停止并请求用户：

- 需要证券账户、密码、Token或其他敏感凭据。
- 需要决定交易品种、风险偏好或资金规模。
- 需要不可逆数据库迁移。
- 需要删除大量数据或文件。
- 两种方案会显著改变产品方向。
- 测试环境缺失，无法验证关键修改。
- 连续三轮被同一外部条件阻塞。
- 达到20轮。

不得因为上下文较长、已经工作一段时间或“看起来差不多”而提前停止。

## 11. Cursor `/loop` 主提示词

在 Cursor Agent 中输入 `/loop`，并附上以下内容：

```text
请严格按照 @docs/Cursor量化系统持续优化执行手册.md，
持续扫描、优化和验证 quant-trading-system 项目。

这是一个长期循环任务，不得完成一个局部修改后就宣布整个任务结束。

每轮必须：

1. 确认 Git 状态：批次起始轮（1/11/21…）须工作区干净；批次内允许本循环未提交改动，但不得含无关修改。
2. 阅读执行手册、.cursor/optimization-progress.md、Git状态和相关代码。
3. 从计算机工程与金融量化两个角度选择一个扫描主题。
4. 找出最多5个有证据的问题并分为P0/P1/P2/P3。
5. 选择一个最高优先级且可以完整验证的问题。
6. 建立修改前基线。
7. 实施最小且完整的修复。
8. 增加或更新回归测试。
9. 运行后端测试、前端类型检查、前端构建及相关运行验证。
10. 验证失败时继续修复，不得跳过或降低标准。
11. 更新 .cursor/optimization-progress.md（批次内 commit 列可填「待批次提交」）。
12. **仅当**当前轮次为 10 的倍数、或停止/用户要求提交时：`git add -A` 批次提交并 push，再次确认工作区干净；其余轮次不 commit。
13. 等待 30 秒后重新扫描并进入下一轮。

循环间隔：**30 秒**（`/loop 30s`）。

优先顺序：

金融正确性和未来函数
→ 行情数据质量（选股输入）
→ 选股因子、评分口径与质量闸（Classic/Oversold/Trend/Comprehensive/MultiDim）
→ 股票池和可交易性（ST、停牌、流动性、涨跌停）
→ 选股结果可解释性与前端筛选体验
→ 打分回测与选股效果验证
→ 单股策略回测与模拟交易
→ 风险管理
→ 测试覆盖、前后端契约
→ 性能、安全和可观测性
→ 构建部署和文档
→ 最后才处理主观样式。

禁止：

- 强行凑满TopN；
- 静默使用随机Mock数据；
- 使用未来财务数据；
- 使用不可成交价格；
- 为了继续循环制造无价值修改；
- 大规模修改无关代码；
- 覆盖用户已有修改；
- 在含**无关**改动的脏工作区继续修改；
- 在批次边界（第 10、20 轮）跳过 commit/push，或只提交部分文件；
- 在批次内（第 1–9 轮）提前 commit（除非用户明确要求）；
- 在测试失败时宣布完成或提交。

只有执行手册中的全部停止条件满足后才可以停止。
最多执行20轮；达到20轮后输出最终报告并停止。
```

## 12. 推荐运行方式

### 本地长任务

优先使用 Cursor `/loop 30s`：批次内连续优化并更新进度，**每 10 轮**（第 10、20 轮）或停止前 **全量 commit + push**，确认工作区干净，间隔 **30 秒** 进入下一轮。

### 远程长任务

可以使用 Cursor Background Agent 或 `/in-cloud`，但必须：

- 使用独立分支。
- 配置可运行的开发环境。
- 不提供生产证券账户凭据。
- 最终由人工审核diff。

### 运行期间人工检查

建议每3至5轮人工检查一次：

- 修改是否仍围绕核心目标。
- 是否出现无意义重构。
- 测试是否真实有效。
- 金融口径是否合理。
- 是否需要业务决策。

长期自主运行不等于无需人工审计。
