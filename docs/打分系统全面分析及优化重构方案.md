# 打分系统全面分析及优化重构方案

## 一、系统总览

当前系统包含 **7 套打分体系**，分布在 30+ 个文件中：

| 打分体系 | 入口服务 | 核心公式 | 因子版本 |
|---------|---------|---------|---------|
| 趋势打分 | StockTrendScoringService | 趋势30 + 乖离20 + 量能15 + 支撑10 + MACD15 + RSI10 | trend_signal_v1 |
| 多维度打分 | MultiDimScoringService | 技术38% + 估值27% + 轮动20% + 行业15% | multi_dim_v2_normalized |
| 超跌反弹打分 | OversoldReboundScoringService | 趋势40 + 量能30 + 超跌30 + 确认15 | oversold_rebound_v2_confirm |
| 综合三维度打分 | ComprehensiveScoringService | 技术30 + 基本面40 + 情绪30 | comprehensive_v2_fundamentals |
| 经典多因子打分 | ClassicFactorCalculator | 趋势35% + 动量20% + 量能20% - 风险25% | classic_v2_cross_section |
| 政策新闻打分 | GeopolicyNewsScoringService | 经典因子 + GDELT宏观叠加 | geopolicy_news_v1 |

## 二、严重问题 (P0 - 必须立即修复)

### 2.1 技术指标计算存在系统性偏差

#### 问题 A：RSI 使用 SMA 而非 Wilder 平滑算法

**位置**: `TechnicalIndicators.java:125-139`

当前实现使用简单移动平均计算涨跌幅均值，这不是标准的 Wilder's RSI。标准 RSI 使用指数平滑：
```
AvgGain[i] = (AvgGain[i-1] * 13 + Gain[i]) / 14
AvgLoss[i] = (AvgLoss[i-1] * 13 + Loss[i]) / 14
```

**影响**: 当前 RSI 值会比标准算法更敏感、波动更大，导致超买超卖信号过早触发。

**修复**: 将 `rsiAt()` 改为 Wilder 平滑算法。

#### 问题 B：KDJ 初始化错误

**位置**: `TechnicalIndicators.java:188-189`

```java
k[0] = rsv[0];  // 错误：应为 50.0
d[0] = rsv[0];  // 错误：应为 50.0
```

**影响**: 前几个 KDJ 值严重失真，需要至少 20-30 根 K 线后才能收敛到合理区间。

**修复**: 初始化为 `k[0] = 50.0; d[0] = 50.0;`。

#### 问题 C：EMA 初始值使用原始价格而非 SMA 种子

**位置**: `TechnicalIndicators.java:21`

```java
out[0] = values[0];  // 第一个 EMA 值等于第一个价格
```

**影响**: MACD 的金叉/死叉信号在前 26 个周期内不准确。

**修复**: 使用前 period 根 K 线的 SMA 作为 EMA 的初始种子值。

#### 问题 D：布林带使用总体标准差而非样本标准差

**位置**: `TechnicalIndicators.java:262`

```java
return n > 1 ? Math.sqrt(var / n) : 0;  // 总体标准差
```

**影响**: 标准差被系统性低估（分母用 n 而非 n-1），导致布林带偏窄，超跌信号触发频率偏高。

**修复**: 改为 `Math.sqrt(var / (n - 1))`。

### 2.2 同一指标存在多套打分标准，结果互相矛盾

这是系统最严重的设计问题。以 RSI 为例，至少有 **5 套不同的评分标准**：

| 文件 | RSI<30 | RSI 30-40 | RSI 40-60 | RSI 60-70 | RSI>70 |
|------|--------|-----------|-----------|-----------|--------|
| ScoringRules.scoreRsi() | **10** | 8 | 7 | 5 | 3 |
| ScoringRules.scoreRsiByStatus() | 10 (超卖) | 8 (强势买入) | 5 (中性) | 3 (弱势) | **0** |
| ScoringRules.scoreRsiOversold() | 10 | 5 | **0** | **0** | **0** |
| TechnicalDocScoring.scoreRsiDoc() | 10 | — | 5 | — | **-10** |
| StockTrendScoringService | 使用 classifyRsiDetailed: >70超买, >60强势买入, ≥40中性, ≥30弱势, <30超卖 → 再用 scoreRsiByStatus |

**同一只股票, RSI=68**:
- 趋势打分: "强势买入" → **8 分**
- 综合打分(TechDoc): "中性" → **5 分**  
- 超跌反弹: **0 分** (RSI>40 不算超跌)

**核心矛盾**: 趋势打分"奖励"RSI 在 60-70 区间的强势特征，而 TechDoc 对超买扣分。这两种逻辑本身在不同策略下可能都有道理——但问题在于它们**共用同一个方法名** `scoreRsi`，导致调用者完全不知道自己在用哪套标准。

MACD 同样存在问题：

| 文件 | 零轴上金叉 | 死叉 | 下穿零轴 |
|------|-----------|------|---------|
| ScoringRules.scoreMacd() | 15 | **0** | **0** |
| TechnicalDocScoring.scoreMacdDoc() | 15 | **-10** | **-15** |

### 2.3 Python 与 Java 超跌反弹权重不一致

| 维度 | Java (OversoldReboundScoringService) | Python (oversold_rebound_scorer.py) |
|------|------|------|
| 趋势权重 | 35% | **40%** |
| 量能权重 | 25% | **30%** |
| 超跌权重 | 25% | **30%** |
| 确认信号 | 15% | **无** |

Python 总分计算 (`total = trend + volume_score + oversold`) 直接三项相加（max 100），而 Java 有归一化到各自满分后再加权和确认信号的逻辑。**两个系统的打分结果不可直接比较**。

### 2.4 情绪面数据完全是技术面的循环推导

**位置**: `EnhancedMarketSentimentService.java`

系统声称评分来自三个独立维度（技术面 + 基本面 + 情绪面），但情绪面的计算完全是技术指标的衍生：

- "新闻舆情" = 价格变化 × 1.5 + 成交量比率 + PE 调整
- "社交媒体热度" = 成交量比率 + 价格涨跌
- "机构观点" = 均线排列 + PE + 行业

**这导致了严重的循环论证**：技术面已经给了高分 → 情绪面也会给高分 → 两者加权后分数更高。基本面和技术面的信息被计算了两次。

举例：如果一只股票放量上涨（技术面给了 25/30），那情绪面的新闻舆情也会因为"价格上涨放量"而给 12-15/15，社交热度也会因为"成交量大幅放大"而给 7-8/8。这导致综合得分中约有 40% 的权重实际上在评估同一件事。

### 2.5 ClassicFactorCalculator 权重和不等于 1

**位置**: `ClassicFactorCalculator.java:18-21`

```java
WEIGHT_TREND = 0.35;
WEIGHT_MOMENTUM = 0.20;
WEIGHT_VOLUME = 0.20;
WEIGHT_RISK = -0.25;  // 负权重
// 总和 = 0.35 + 0.20 + 0.20 + (-0.25) = 0.50
```

四维权重加起来只有 0.50，这意味着最终得分被系统性地压缩到了 0-50 区间，而非预期的 0-100。如果意图是 "风险作为惩罚项"，正确写法应该是：

```java
finalScore = WEIGHT_TREND * trend + WEIGHT_MOMENTUM * momentum 
           + WEIGHT_VOLUME * volumeScore - WEIGHT_RISK_PENALTY * riskPenalty;
// risk 应该用正权重做减法，而非负权重做加法
```

### 2.7 MultiDimScoringService 权重不收敛

**位置**: `MultiDimScoringService.java:306-318`

```java
double techWeight = Math.max(0.1, dynamicWeights.technicalWeight() - 0.10); // 0.23~0.3
double rotationWeight = 0.05;
double industryWeight = 0.05;
// composite = techNorm * techWeight + fundNorm * fundWeight 
//            + sentNorm * sentWeight + rotNorm * 0.05 + indNorm * 0.05 + industryAdjustment
```

问题：
1. 五个权重的和不等于 1.0（`techWeight + fundWeight + sentWeight + 0.05 + 0.05 ≈ 0.63~0.95`），导致综合分偏低
2. 传给 `CompositeScoringService.scoreComposite()` 的权重和实际使用的权重**不一致**，导致 `compositeResult.investmentAdvice()` 和 `e.setSuggestion()` 基于不同分数给出建议
3. `industryAdjustment` 直接加到综合分上（而非作为权重调整），+5 分对于银行股是巨大的系统性偏差

## 三、重要问题 (P1 - 应尽快修复)

### 3.1 行业调整直接加分，破坏评分公平性

银行股无条件 +5 分，新能源 +4 分。这意味着：
- 一只各方面都很差的银行股可能比一只各方面都不错的普通行业股票得分更高
- 行业调整应该影响估值中枢（如银行股 PE 天然偏低），而不是直接在总分上加分

正确做法应该是调整估值维度的基准（如银行股 PE<8 才算低估，而非 PE<15），或在行业内做 percentile 排名后加分。

### 3.2 动态权重在震荡市中基本面权重过低

震荡市: 技术 40% + 基本面 20% + 情绪 40%

当市场是震荡市时，基本面权重只有 20%。这意味着在 A 股最常见的震荡市环境中，公司的盈利能力、财务健康几乎不被考虑。但震荡市恰恰是最需要基本面选股的场景（因为没有趋势可以跟随）。

### 3.3 市场环境判断过于简单

**`ComprehensiveScoringService.inferMarketEnvironment()`** (line 281-291) 只用 60 日涨跌幅判断：
- >20% = 牛市
- <-20% = 熊市
- 其他 = 震荡市

这完全没有考虑：
- 市场波动率（VIX 代理）
- 成交量趋势
- 市场广度（上涨/下跌家数比）
- 融资融券余额变化

而 `MarketEnvironmentAnalyzer` 有更完善的实现，但 `ComprehensiveScoringService` **没有使用它**，直接自己写了一个极其简化的版本。

### 3.4 趋势打分中乖离率逻辑已修复

**原分析有误**：scoreBias 路径经过重新验证是可到达的——强牛市中 bias 在 threshold 和 effective 之间时会正确返回 10 分。已重构为更清晰的逻辑结构，增加了代码可读性。

### 3.5 综合打分复用 StockTrendScore 实体导致字段语义混乱

**位置**: `ComprehensiveScoringService.java:467-484`

```java
e.setScoreTrend(result.technicalScore());   // 存的是技术面分数
e.setScoreBias(result.fundamentalScore());   // 存的是基本面分数
e.setScoreVolume(result.sentimentScore());   // 存的是情绪面分数
e.setScoreSupport(result.technicalDetail().maScore()); // 存的是均线分数
e.setScoreMacd(result.technicalDetail().macdScore());  // MACD
e.setScoreRsi(result.technicalDetail().rsiScore());    // RSI
```

`StockTrendScore` 的字段名是 `scoreTrend`/`scoreBias`/`scoreVolume`/`scoreSupport`，但综合打分往里面存的是完全不同含义的数据。这是严重的数据语义污染——任何读取该表的人都无法确定字段的真实含义。

### 3.6 超跌反弹 totalScore 和 weightedScore 双轨制

**位置**: `OversoldReboundScoringService.java:535-544`

```java
// totalScore: 直接缩放到各自满分后相加
double totalScore = trendScore * 35.0/40.0 + volumeScore * 25.0/30.0 
                  + oversoldScore * 25.0/30.0 + confirmScore;

// weightedScore: 按百分比归一化后加权
double weightedScore = (trendScore/40.0)*100*0.35 + (volumeScore/30.0)*100*0.25 
                     + (oversoldScore/30.0)*100*0.25 + (confirmScore/15.0)*100*0.15;
```

这两个分数的计算逻辑不同，但在 `pickTopN` 中使用 `weightedScore` 排序、在质量闸中使用 `totalScore`。这导致**排名和筛选标准不一致**——一只股票可能按 weightedScore 排第一但不满足 totalScore 的质量闸要求。

### 3.7 RSI 周期不统一

| 使用位置 | RSI 周期 |
|---------|---------|
| ScoringConstants.RSI_PERIOD | **14** |
| StockTrendScoringService | **12** (硬编码) |
| OversoldReboundScoringService | **14** |
| TechnicalDocScoring | **14** |

趋势打分硬编码使用 RSI12，与常量定义不一致。

## 四、中等问题 (P2 - 应逐步优化)

### 4.1 缺少 A 股特色因子

当前评分系统完全没有考虑 A 股市场的独特机制：
- **涨跌停限制** (±10% 主板, ±20% 科创/创业)：连续涨停/跌停的股票技术指标会失真
- **北向资金**：外资流向对 A 股有显著影响
- **融资融券余额**：杠杆资金情绪
- **龙虎榜**：游资和机构行为
- **解禁压力**：大小非解禁对股价的影响

### 4.2 缺少波动率调整和仓位管理

系统只打分不计算：
- 基于 ATR 的止损位
- 基于波动率的仓位建议
- 收益风险比（reward-to-risk ratio）
- 最大持仓集中度控制

### 4.3 信号衰减未实际应用

`SignalDecay.java` 已经定义了信号衰减函数，但主流打分服务都没有调用。所有 K 线数据在回溯窗口内被等同对待——260 天前的数据和昨天的数据权重一样。

### 4.4 截面标准化默认关闭

`scoring.cross-section.enabled: false` 意味着所有股票的分数是在绝对尺度上比较的。在牛市中所有股票分数偏高，熊市中偏低，导致跨时期的分数不可比。

### 4.5 缺少因子共线性检测的实际应用

`FactorCollinearityChecker.java` 已实现但未被任何打分服务调用。情绪面的推导因子和技术面因子之间必然存在高度共线性，但系统没有检测也没有修正。

## 五、从金融量化角度的专业评审

### 5.1 打分体系的理论基础问题

#### 趋势打分的致命缺陷：奖励超卖但不区分趋势方向

趋势打分中 RSI<30(超卖) 获得满分 10 分，这在逻辑上是**自相矛盾**的：
- 趋势打分的目标是找到"趋势向好"的股票
- 但 RSI 超卖意味着股票极度弱势
- 在下跌趋势中，RSI 可以长期维持在超卖区域（"超卖可以更超卖"）

正确的做法应该是：
- **趋势跟随策略**：RSI 在 40-70 区间给高分（趋势中的健康回调或强势延续）
- **均值回归策略**：RSI<30 才应该给高分（预期反弹）

当前系统试图用一个分数同时服务两种矛盾的交易逻辑。

#### 权重设计缺乏实证依据

所有维度的权重（技术 38%、估值 27%、轮动 20%、行业 15%）都是**人为拍定的**，没有经过历史回测验证其有效性。在量化交易中，权重的确定应该基于：
1. IC 分析（信息系数）
2. 因子收益率回测
3. 因子衰减速度
4. 不同市场环境下的因子表现差异

#### 综合打分中基本面 40% 权重过高——但对 A 股短期交易适用性存疑

基本面（PE/PB/ROE/负债率）反映的是公司的长期内在价值，但对于 2-5 天的短期交易决策：
- PE 在 5 天内几乎不变
- ROE 是季度数据，几个月不变
- 这意味着基本面维度在连续多个交易日中给出的分数完全相同

这导致：如果一只股票基本面得分高，它会在连续数周内持续获得高分，无论技术面是否恶化。这不是一个有效的短期交易信号。

**建议**：短期交易中基本面权重的合理范围是 10-15%，而非 30-40%。或者对基本面因子做时间衰减，离财报发布日越远，权重越低。

### 5.2 技术指标使用问题

#### MACD 参数 (12, 26, 9) 适合日线但不适合所有周期

这是日线标准参数，但系统没有针对不同持股周期做参数调整：
- 2-3 天短线应使用 (6, 13, 5)
- 周线应使用不同参数

#### 缺少关键的动量因子

系统没有包含以下在 A 股实证有效的因子：
- **换手率因子**：异常换手率对短期收益有预测能力
- **动量加速度**：动量的变化率（二阶导）
- **隔夜收益率**：A 股 T+1 制度下，隔夜跳空包含重要信息
- **量比**：当日成交量/5日均量的比值（已有但未独立打分）

#### 均线支撑判断过于简单

`maSupport()` 只要价格在均线上方 2% 以内就算支撑。但真正的均线支撑还需要考虑：
- 价格是否多次在该均线附近获得支撑（支撑确认）
- 均线本身的斜率（走平或向下的均线不构成有效支撑）
- 回调至均线的成交量是否萎缩

### 5.3 超跌反弹策略的量化评估

超跌反弹策略总体上设计较为合理，但也存在以下问题：

**优点**：
- 多维超跌确认（收益率为负 + 均线下方 + 周线阴线 + RSI/布林带/分位数）
- 有确认信号机制（底背离、量能确认、反转K线）
- 有质量闸过滤

**缺点**：
- 没有区分"技术性超跌"和"基本面恶化的合理下跌"
- 没有考虑下跌过程中的成交量结构（缩量下跌 vs 放量下跌的区别对待不够精细）
- 缺少反弹目标位和止损位的计算
- 确认信号中 MACD 底背离检测算法过于简化（只比了两个低点）

## 六、重构方案

### 阶段一：技术指标计算修复 (P0)

```
1. RSI 改为 Wilder 平滑算法
2. KDJ 初始化改为 K[0]=50, D[0]=50
3. EMA 使用 SMA 种子
4. 标准差改为样本标准差 (n-1)
5. 统一所有 RSI 调用为 RSI14（修复趋势打分中的硬编码 RSI12）
6. 修复 ClassicFactorCalculator 权重求和问题
```

### 阶段二：评分标准统一 (P0)

```
1. 建立单一评分标准枚举 ScoreStandard，所有打分服务共用
2. 删除 TechnicalDocScoring 中的重复评分方法
3. 删除 MarketSentimentScoring (已废弃)
4. Python 与 Java 超跌反弹逻辑对齐
5. 行业调整从"直接加分"改为"估值基准调整"
```

### 阶段三：情绪面重构 (P1)

```
1. 情绪面指标与价格/量价指标解耦
2. 接入真实数据源(或明确标注为"不可用")
3. 短期方案：情绪面降权至 10%，在获取真实数据前不参与核心打分
4. 引入因子共线性检测，对共线性 >0.7 的因子做降权或合并
```

### 阶段四：A 股特色因子引入 (P2)

```
1. 添加涨跌停状态检测（涨停/跌停股跳过或特殊处理）
2. 添加换手率因子
3. 添加北向资金因子（如有数据源）
4. 添加异常波动标记
```

### 阶段五：权重体系实证优化 (P2)

```
1. 建立因子 IC 回测框架
2. 基于历史数据计算各因子的 IC 和 IR
3. 按市场环境分段统计因子有效性
4. 基于实证结果调整权重
```

## 七、建议的代码结构重构

### 当前架构问题

```
ScoringRules (静态工具类)
├── 包含趋势打分规则
├── 包含超跌反弹规则  
├── 包含基本面规则
├── 包含投资建议规则
└── 包含行业调整规则
    ↓ 被 7 个不同服务调用，每个服务有自己的补充规则
```

### 建议的新架构

```
scoring/
├── indicators/
│   ├── TechnicalIndicators.java     (修复后的指标计算)
│   └── IndicatorValidator.java      (指标质量校验)
├── dimensions/
│   ├── TechnicalDimension.java      (技术面维度 - 唯一入口)
│   ├── FundamentalDimension.java    (基本面维度 - 唯一入口)
│   ├── SentimentDimension.java      (情绪面维度 - 唯一入口)
│   └── RiskDimension.java           (风险维度)
├── standards/
│   └── ScoreStandards.java          (唯一的评分标准定义)
├── strategies/
│   ├── TrendScoringStrategy.java    (趋势策略)
│   ├── OversoldReboundStrategy.java (超跌反弹策略)
│   ├── MultiDimStrategy.java        (多维度策略)
│   └── CompositeStrategy.java       (综合策略)
├── normalization/
│   ├── CrossSectionNormalizer.java  (截面标准化)
│   └── SignalDecay.java             (信号衰减)
├── validation/
│   └── FactorCollinearityChecker.java
└── config/
    └── ScoringWeights.java          (权重配置 - 支持动态加载)
```

核心原则：
1. **每个维度只有一个评分入口**，避免重复定义
2. **策略组合维度**，而非策略定义评分规则
3. **权重与算法分离**，权重可配置、可回测
4. **Python 和 Java 共享同一套计算逻辑**（通过单元测试验证一致性）
