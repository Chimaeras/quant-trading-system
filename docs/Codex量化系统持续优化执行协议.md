# Codex 量化系统持续优化执行协议

## 1. 用途

本文件用于指导 Codex 对 `quant-trading-system` 进行长期、循环、可验证的持续优化。

Codex 不需要照搬 Cursor 的 `/loop` 命令。推荐使用以下组合实现同等效果：

```text
Codex长期目标（Goal）
  + 本执行协议
  + 持久化进度文件
  + 每轮验证
  + 自动续跑
  + 明确停止条件
```

如果希望每天或每隔固定时间执行一轮，则使用 Codex Automation。

---

## 2. 依赖文档

开始工作前必须完整阅读：

1. `docs/Cursor量化系统持续优化执行手册.md`
2. 本文件
3. `README.md`
4. `docs/Codex量化系统持续优化进度.md`，如果已经存在
5. 当前 Git 状态和 Git diff

`Cursor量化系统持续优化执行手册.md` 定义了完整的：

- 金融量化审查框架；
- 软件工程审查框架；
- P0/P1/P2/P3优先级；
- 数据、股票池、因子、策略、回测、风控和QMT要求；
- 里程碑与验收标准。

本文件只补充 Codex 的长期执行方式，不复制上述全部内容。

## 3. 长期目标

将当前项目逐步建设成一套可信赖的个人量化研究与交易决策辅助系统，优先形成：

```text
可信行情与财务数据
→ 历史时点股票池
→ 可解释因子
→ 严格回测
→ 样本外验证
→ 每日买入/持有/卖出/无机会信号
→ 目标仓位与风险提示
→ 人工执行和实际绩效记录
→ QMT只读对账
→ 受控自动交易
```

当前优先级：

```text
金融正确性
→ 数据可信度
→ 回测可信度
→ 信号有效性
→ 风险管理
→ 测试保障
→ 工程质量
→ 自动交易
```

不得优先建设与当前阶段无关的微服务、复杂机器学习、高频交易或华丽页面。

## 4. Codex循环模型

一次长期目标由多个“目标回合”组成，每个回合完成一轮闭环。

```text
读取进度
→ 扫描一个主题
→ 发现候选问题
→ 选择最高优先级问题
→ 建立修改前证据
→ 实施最小完整修复
→ 增加回归测试
→ 编译与运行验证
→ 更新进度文件
→ 判断停止条件
→ 未满足则进入下一目标回合
```

每个回合只处理：

- 一个独立问题；或
- 一组不可分割的强相关问题。

不得在一个回合内同时重构多个无关模块。

---

## 5. 每轮执行步骤

### 第一步：读取状态

必须检查：

- 执行协议；
- 优化手册；
- 进度文件；
- Git状态；
- 用户已有修改；
- 上一轮测试结果；
- 上一轮残余风险。

### 第二步：选择扫描主题

每轮只选择一个：

1. 未来函数与金融正确性；
2. 数据质量与数据时点；
3. 股票池与可交易性；
4. 因子计算与评分口径；
5. 回测成交模型；
6. 组合与仓位管理；
7. 风险控制；
8. 测试覆盖；
9. 前后端契约；
10. 数据库与并发；
11. 性能；
12. 安全；
13. 日志、监控与部署；
14. 文档一致性。

### 第三步：提供证据

修改前必须明确：

- 问题位置；
- 复现方式；
- 当前错误行为；
- 对金融结果或系统稳定性的影响；
- 优先级；
- 修改风险；
- 验证方法。

没有证据的问题不进入修改阶段。

### 第四步：实施修改

要求：

- 保留用户无关修改；
- 不进行破坏性Git操作；
- 不自动提交或推送；
- 不修改任务范围外的代码；
- 不用Mock或异常吞噬掩盖错误；
- 数据库变更考虑旧数据兼容；
- 金融计算写明口径和时点；
- API变更同步前端类型和文档。

### 第五步：验证

最低验证：

```powershell
mvn test '-Dskip.frontend.build=true'

cd modules/web
npm exec vue-tsc -- --noEmit
npm run build
```

涉及Python时：

```powershell
python -m pytest
```

涉及API或页面时：

```text
启动应用
→ 验证目标API
→ 验证目标页面
→ 检查后端日志
→ 检查浏览器错误
```

测试失败时必须继续修复，不得通过删除测试、降低断言或跳过检查宣布成功。

### 第六步：记录

每轮必须更新：

```text
docs/Codex量化系统持续优化进度.md
```

记录内容：

- 当前轮次；
- 扫描主题；
- 发现的问题；
- 修改文件；
- 新增测试；
- 验证结果；
- 未解决风险；
- 下一轮建议；
- 连续无新增P0/P1/P2轮数。

### 第七步：继续或停止

未满足停止条件时，不得因为完成一个局部修复就结束长期目标。

---

## 6. 停止条件

满足以下全部条件，Codex才可以将长期目标标记为完成：

1. 连续两轮完整扫描没有发现新的P0、P1或P2问题；
2. 进度文件不存在未处理P0或P1；
3. 后端测试全部通过；
4. 前端类型检查通过；
5. 前端生产构建通过；
6. Python测试通过，如果Python模块仍被使用；
7. 核心API冒烟通过；
8. 核心页面冒烟通过；
9. 剩余问题只有P3、主观风格或需要用户决策的事项；
10. 已输出最终审查报告。

满足以下任一条件时暂停并请求用户，而不是擅自决定：

- 需要证券账户、密码、Token或API Key；
- 需要决定交易对象、策略方向、风险偏好或资金规模；
- 需要删除大量数据；
- 需要不可逆数据库迁移；
- 需要启用真实自动交易；
- 不同方案会显著改变产品方向；
- 外部服务或测试环境持续不可用；
- 同一阻塞条件连续出现三轮；
- 达到20轮。

“工作时间较长”“上下文较长”或“已经修了很多问题”不是停止理由。

## 8. 在Codex中启动长期目标

推荐在项目线程中发送：

```text
请为当前项目创建一个长期目标：

持续优化 E:\Project\quant-trading-system，
严格按照
@docs/Codex量化系统持续优化执行协议.md
和
@docs/Cursor量化系统持续优化执行手册.md
执行。

每个目标回合只完成一轮“扫描—证据—修复—测试—记录”闭环。
每轮更新 docs/Codex量化系统持续优化进度.md。
未满足停止条件时持续进入下一回合。
最多20轮。

不要自动提交、推送、创建PR或启用真实交易。
```

```text

执行一轮优化，不创建长期目标。
完成后更新进度文件并停止。
```

## 9. 使用Codex Automation分批迭代

如果不希望一个线程连续运行，可以创建定时自动化，让Codex每天执行一轮。

推荐自动化要求：

```text
名称：量化系统每日优化一轮
工作目录：E:\Project\quant-trading-system
频率：每天一次，或仅工作日执行
运行环境：独立worktree优先
每次范围：只完成一轮
```

自动化提示词：

```text
阅读：
1. docs/Codex量化系统持续优化执行协议.md
2. docs/Cursor量化系统持续优化执行手册.md
3. docs/Codex量化系统持续优化进度.md

仅执行一轮最高优先级优化：

扫描一个主题
→ 提供问题证据
→ 修复一个最高优先级问题
→ 增加回归测试
→ 完成全部相关验证
→ 更新进度文件
→ 输出本轮报告。

不要自动提交、推送、创建PR或启用真实交易。
如果需要用户业务决策，只记录到进度文件，不做假设性修改。
```

自动化适合分批、隔离地持续检查；涉及同一工作区连续修改时，长期目标更自然。

## 10. 建议的执行策略

### 方案A：长期目标

适合：

- 希望Codex持续工作；
- 各轮之间需要紧密上下文；
- 允许在当前工作区连续修改；
- 希望达成停止条件后自动结束。

### 方案B：每日自动化

适合：

- 每天只处理一个问题；
- 希望每轮独立审查；
- 希望使用worktree隔离；
- 不急于一次完成。

### 方案C：先目标后自动化

推荐实践：

1. 先用长期目标集中处理P0/P1；
2. 人工审核；
3. 再用每日自动化处理新增问题和维护性工作。

---

## 11. 人工检查点

每3至5轮暂停一次，向用户汇报：

- 已完成问题；
- 当前测试情况；
- 金融可信度变化；
- 代码规模变化；
- 是否出现架构漂移；
- 是否需要业务决策；
- 下一阶段建议。

长期自治不代表可以省略人工审计，尤其是金融策略、风险参数和实盘接口。
